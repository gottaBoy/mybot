# 车端远控视频：最终推荐方案与落地步骤

状态：基于用户现状的推荐方案，等待现场版本与管道核验；尚未实施或验证。
本记录是独立技术议题，不改变 mybot 产品主线、Workflow 交付范围或119项台账。
资料范围：用户陈述、官方文档和协议规范；未访问车辆、正式服务器或现场网络。
新增明确要求：车端到ZLM、ZLM到浏览器等每段都须维护连接；断开或停止出新帧时，
应快速通知、自动恢复并验证实际画面恢复，不得静默卡住。具体设计见第6节。
自顶向下的网络分段、数据字典、定位规则及O0-O9子任务，见
[可观测性与落地任务拆解](REMOTE_VIDEO_OBSERVABILITY_BREAKDOWN.md)。
落地以配套文档第2.1-2.4节的可获得性分级、逐段难点和最小观测点为准：
先核验实际接口，缺数据时合并定位区间，完整逐帧追踪及运营商内部指标不作为首版前提。
按组件的明确实现入口与不可外推项见配套文档第2.5节；可建设不等于已接入现场。

## 1. 结论与选择

最终推荐采用：**保留 ROS2、GStreamer 和 ZLM；车端控制编码器，主动通过 WebRTC
上传到 ZLM；浏览器继续使用 WebRTC。建立车端自适应、两段链路观测和故障恢复闭环。**

每段连接配有独立生命周期管理：保活、媒体进展检查、通知、重连和恢复确认。
以减少不必要断链为目标；实际网络中断不保证零断链，因此断链后的通知和恢复是必交付项。

这是当前目标下优先验证的工程选择，不是已经证明在现场性能最优。
落地顺序是：核验版本 -> 测清现有链路 -> 打通编码器控制 -> WebRTC 上传对照测试 ->
通过验收后小范围切换。现有 RTSP 链路在验证期间保留，作为基线和回退路径。

选择理由与边界：

- 复用已有采集、编码、云端分发和浏览器，避免先替换整套流媒体服务器。
- 重点改变跨5G的媒体发送与反馈，不把“拉改推”本身当作性能优化。
- 让网络反馈真正影响源端编码量，不只是把固定码率 RTSP 重新封包。
- 采用成熟 WebRTC/GStreamer 实现；不自行重写 RTP、拥塞控制或媒体服务器。[S1][S2]
- 先解决排队、反馈、恢复及测量，再判断是否需要双运营商、服务器区域调整或硬件改造。
- 完全断网时无法持续获得实时图像；优化目标是控制额外积压、明确画面失效，并在恢复后
  尽快回到实时，不能承诺消除所有卡顿。[S2]

官方当前文档不等于现场2025年构建的能力清单。

## 3. 目标架构

```text
摄像头 / ROS2
    |
    v
车端 GStreamer：有界采集队列 -> 可控制的编码器 -> WebRTC 发送
    |                                                  |
    | 本地监测 / 参数执行                              | 跨5G主动发布
    v                                                  v
车端策略控制器 <---- 上传链路反馈 --------------------- ZLM
    |                                                  |
    | 帧关联、队列、温度、模组状态                      | WebRTC 分发
    v                                                  v
独立轻量遥测 / 事件服务 <-------------------------- 浏览器播放器
    |                                             getStats / 呈现观测
    v
统一故障时间线、对照报告、运维看板
```

### 3.1 车端媒体路径

优先接入原始帧或直接控制已有源编码器，保持一次编码。
如果短期只能从车内 RTSP 取已编码视频，应补通对原编码器的参数控制；
没有源编码器控制时，只做重封包并不构成完整自适应。
不默认解码再编码，只有实测兼容性或能力缺口要求时才采用，并记录新增耗时和算力。

上传优先使用实际兼容版本的 `whipclientsink` 或带 ZLM 信令适配的 `webrtcsink`。
`webrtcsink` 默认信令并非 ZLM 信令，不能把二者直接连接当作已兼容。
若现有组件不满足，再评估 `webrtcbin` 加适配器；单有 `webrtcbin` 不代表应用已经完成
拥塞控制、码率联动和故障恢复。[S1][S4]

WHIP 是 WebRTC 的接入信令方式，不是使用 HTTP 传视频。
ZLM 当前官方 API 文档列出 WHIP，但2025年现场构建的端点、SDP、生命周期和反馈能力
仍需核验，不能直接照抄当前文档的配置。[S5]

### 3.2 两段独立反馈

分别验证“车端 -> ZLM”和“ZLM -> 浏览器”的媒体传输、RTCP、重传及拥塞反馈。
不能假设 ZLM 自动把浏览器 TWCC、RTP 扩展、帧号或原始采集时间透传给车端。
SDP 中声明能力只算协商证据，还需证明实际反馈包到达、被消费并改变编码/发送行为。

浏览器网络或解码性能差，不应未经区分就让所有观看者和车端一起降级。
首版明确一个主操作席；多观看者的单路码流共享、不同清晰度与转码需求另行验证。

## 4. 随流追踪与监测设计

推荐“帧关联 + 协议统计 + 独立遥测”结合，不将温度、全部信号采样塞入每个 RTP 包。
RTCP 提供协议层接收质量报告，不能单独测出完整采集到屏幕延迟。[S6]
遥测需独立于视频解码，视频卡住时仍能判断设备是否存活；它仍可能共享同一物理5G链路，
不能被描述为网络冗余。

| 位置 | 采集内容 | 用途 |
| --- | --- | --- |
| 摄像头 / ROS2 | 可验证源时间戳、应用自建序号/到达频率、可取队列/丢弃 | 判断采集/接入进展；不把ROS Header.frame_id当逐帧ID |
| 编码前后 | 入出时间、实际码率、编码耗时、关键帧、各队列驻留时间 | 判断编码与本地排队 |
| 车端发送 | 实际承载、发送速率、RTT、反馈新鲜度、丢包/重传、发送积压 | 上传链路自适应 |
| ZLM 输入与输出 | 收包/收帧间隔、帧关联、转发驻留、每段会话统计 | 区分上传与分发故障 |
| 浏览器 | 接收/解码/呈现帧率、丢帧、缓冲、冻结、反馈与连接状态 | 区分下行、解码和呈现 |
| 车端系统与模组 | 温度、降频、CPU/GPU、RSRP/RSRQ/SINR、注册及小区事件 | 辅助归因与限制负载 |

上表是目标观测点清单，不是已确认具备或首版必须全部取得的接口。
首版优先车端输出、ZLM可确认的收流进展、浏览器收包/解码进展；
缺ZLM输出探针时保留云端及下行的合并区间，不虚构内部转发时间。

实施规则：

- 帧身份至少包含 `stream_id + session_epoch + frame_id`；重启或重连后不能串帧。
- 本机阶段耗时用单调时钟；跨机使用经校准的时间并记录同步误差和时钟跳变。
- 首版在测试画面叠加源帧号/时间，用录像验证真正的画面新鲜度；测量口径写明是源采集
  还是应用接收时间。显示提交时间不等于物理屏幕发光时间。
- 后续才做结构化时间戳/帧号扩展及 ZLM 映射；逐段验证保留和浏览器可访问性。
  写入 RTP 扩展或 H.264 SEI，不等于浏览器能直接读取。
- 浏览器优先使用 `getStats()`；字段不支持则记未知。累计计数转为窗口增量，处理重连/
  counter reset。窗口平均缓冲延迟使用 `ΔjitterBufferDelay / ΔjitterBufferEmittedCount`，
  不能直接把累计值当作当前延迟。[S7]
- 模组接口、温度阈值以具体厂商/设备文档为准；小区 ID 改变只是相关事件，不能单独
  证明发生了造成断流的切换。缺失信号数据不补0。
- ping/curl 保留为辅助证据。curl 的 DNS、建连、TLS、首字节、总耗时分别记录，
  不把 `time_total` 当 RTT；不在生产链路周期性跑满带宽探测。[S8]

### 4.1 分段定位交付

按配套拆解文档建立S0-S8媒体边界与C0/C1信令/遥测边界，
重点区分车端内核/模组、上传网络、云端接收、ZLM内部、下行网络和浏览器处理。
每个故障输出“异常区间、同窗证据、证据等级、下一步检查与恢复动作”，
无运营商/中间节点探针时不声称能精确定位某个基站或公网路由。
从L0业务可用性逐级下钻到L1拓扑、L2指标与L3原始证据；缺失指标记未知，不补0。

## 5. 自适应控制设计

### 5.1 一个快速控制器，加一组上层限制

媒体侧使用已验证的拥塞控制实现，依据上传反馈调节发送/编码速率。
车端策略控制器负责温度、采集/编码负载、画质底线和多摄像头预算；云端负责策略管理、
诊断和长期统计，不承担必须等云端响应的快速降级。

概念约束为：

```text
可用媒体预算 = min(网络允许预算, 设备负载预算, 业务配置上限)
```

实现上通过组件支持的上限/分配接口协作，不让自写规则与 GCC 同时反向修改同一个
编码器码率。GStreamer 官方说明 `webrtcsink` 会保留拥塞控制所需的码率控制权。[S1]
多摄像头预算还需计入实际 RTP/加密开销、重传和保护数据，不能只加编码器目标码率。

### 5.2 降级与恢复

| 状态 | 判断依据 | 动作 |
| --- | --- | --- |
| 正常 | 队列、反馈和实际画面新鲜度稳定 | 保持当前预算 |
| 拥塞 | 反馈恶化、队列驻留增长、实际帧变旧 | 快速降码率；必要时降低非关键视角帧率 |
| 设备受限 | 编码耗时或经确认的温度/降频限制 | 限制编码负载，区分SoC和模组问题 |
| 断流 / 反馈失联 | 超过经业务确认的时限 | 标记画面失效；进入受控重连/恢复 |
| 恢复观察 | 新帧与反馈恢复，队列已回落 | 小步恢复，保持观察期，避免反复升降 |

所有阈值由现场基线、设备限制及业务新鲜度要求确定。
不得把丢包10%、85摄氏度、GOP1秒或500ms缓冲当作通用生产处方。
分辨率/帧率变更可能需要重协商或重建，必须单独验证；首版优先采用已验证的动态码率。
关键帧请求需合并和限频，避免恢复时关键帧突发再次挤满链路。

### 5.3 队列与旧帧处理

逐个盘点 ROS2、appsrc、GStreamer queue、编码器、socket、ZLM、浏览器缓冲。
队列设定容量和驻留时间预算；GStreamer queue 可查询深度并配置阻塞/丢弃行为。[S9]

优先在编码前的原始帧队列淘汰过期帧；不能在 H.264 等压缩数据路径随意丢 buffer，
因为帧之间可能存在解码依赖。编码后清理必须识别访问单元和可解码恢复边界。
目标是恢复后尽快拿到新画面，而不是追播断流期间积累的旧内容。

## 6. 逐连接保活、快速通知与自动恢复

### 6.1 每段单独负责

每条连接区分“传输健康”和“媒体进展”两类状态。
心跳、会话存在或ICE connected，不足以证明画面是新的。
信令服务暂时失效也不等于已经建立的媒体必然断开；不能因此无条件销毁仍有效的视频。[S11]

| 段 / 恢复责任方 | 监测依据 | 首选恢复动作 |
| --- | --- | --- |
| 摄像头/ROS2 -> GStreamer，车端 | 源帧号和时间推进、bus error/EOS、编码进度 | 修复受影响采集/编码分支；不先重启整车或所有摄像头 |
| 车端 -> ZLM，车端发布管理器 | 本端发送/反馈进展、连接状态、ZLM收流进展 | 短暂抖动先保留会话并降级；失败后重建上传会话，恢复可解码起点 |
| 当前RTSP拉流过渡链路，ZLM拉流管理器 | 拉流错误、媒体收包/帧进展、源注册生命周期 | 核实该commit已有重连行为，指定唯一重试责任方；避免两套拉流器同时建连 |
| ZLM -> 浏览器，播放器会话管理器 | ICE/PeerConnection事件、收包/解码/呈现进展、画面年龄 | 按证据区分上传停流、下行断链和解码阻塞，仅恢复受影响部分 |
| 信令/遥测，双方连接管理器 | 请求期限、心跳、最近事件序号、认证状态 | 独立重连并补读当前状态/事件；不能以遥测重连触发全链路重启 |
| ZLM进程/节点，运维与两端管理器 | 进程健康、会话批量异常、输入输出停顿 | 重启后的车端重发与浏览器重订阅有序恢复；保留稳定逻辑流身份 |

保活使用实际版本支持的RTSP/WebRTC机制，并核对NAT、代理、负载均衡和服务端空闲超时；
不依靠高频curl代替媒体健康检查，也不随意将所有超时放大为几十秒。
车端管理器可先加入现有RTSP架构，不必等上传协议迁移。

### 6.2 状态机与恢复顺序

```text
CONNECTING -> LIVE -> DEGRADED / STALLED -> RECONNECTING -> RECOVERING -> LIVE
                    |                         |
                    +------> BLOCKED <--------+
                         认证/权限/配置被拒
```

`STALLED` 表示预期应有的媒体进展停止，可能仍有传输连接；不等于已经知道故障发生在哪一段。
新帧持续到达但画面超龄属于媒体质量降级，不能单凭超龄销毁会话。
WebRTC `disconnected` 可能是暂态，不能收到一次就立即重建；`failed` 或媒体进展停滞达到
应用期限且证据指向该段需重建时进入恢复。应用媒体看门狗不能只等协议层最终超时。[S11]

恢复流程：

1. 当地立即标记画面失效，记录故障ID、证据和最后新帧时间，通知不等待恢复成功。
2. 确定受影响段。若ZLM输入停流而浏览器下行连接健康，应等待上游恢复，
   不反复销毁浏览器会话；若仅一个浏览器故障，不重启车辆上传。
3. 支持并验证过ICE restart时，可先尝试受控restart；否则关闭旧peer、重新信令建连。
   不能假定2025年ZLM/GStreamer支持相应重协商或WHIP会话更新。
4. 每段同一时刻仅一个恢复任务；所有请求带期限、取消信号和session epoch。
   旧会话的迟到响应不得覆盖新会话，也不得留下两个同名发布者。
5. 在网络可达时立即首试；后续采用有抖动的退避，建议实验起点为0.5/1/2/5秒并封顶。
   每个请求自身也有超时。确认网络恢复后可提前唤醒一次；持续故障保持节流与不可用状态。
6. 清理过期积压，按解码依赖恢复；通过实际支持的路径合并请求关键帧，
   不让多个浏览器独立制造车端关键帧风暴。
7. 收到新会话的新鲜可解码/可呈现帧后才进入 `RECOVERING`，连续满足V1新鲜度与稳定
   窗口后才宣布 `LIVE`。HTTP200、SDP成功或ICE connected均不单独代表恢复成功。

401/403等认证/权限拒绝进入 `BLOCKED`，停止盲目重试并明确通知；
凭证更新后才重新尝试。流尚未注册与永久配置错误也需分开，不能永久显示“正在连接”。
页面进入后台可能限制定时器，应记录可见性；恢复前台时重新核对媒体，
不能把后台检测间隔宣称为可靠的故障通知SLA。

### 6.3 通知方式与时间预算

即时通知首先是操作界面的失效标识与状态事件，运维外部通知再按确认的渠道接入。
不依赖同一条已断视频连接传递唯一告警：

- 浏览器本地看门狗直接提示“画面变旧/断流，正在恢复”，同时显示最后新帧年龄。
- 车端和ZLM分别产生故障/恢复事件，经独立遥测连接汇总；全网断开时允许远端收不到，
  本地仍须检测并采取已定义的失联处置。
- 恢复后先补读权威当前状态，再按单调事件序号补齐记录；去重同一故障，
  旧事件不能覆盖新状态。断链事件与恢复事件保留同一故障关联ID。
- 事件包含车辆/摄像头、逻辑流、会话epoch、连接段、首次异常时间、检测时间、
  原因证据、恢复次数及当前状态；无法定位的段明确为未知。

建议在V1讨论以下实验起点，属于待确认目标，不是已测承诺或驾驶安全阈值：

| 指标 | 实验候选与计时口径 |
| --- | --- |
| 画面超龄提示 | 超过业务允许画面年龄后，前台页面在一个本地检查周期内提示；检查周期可先试100-250ms |
| 无媒体进展检测 | 按期望帧率设阈值；可先试0.5-1秒，主动暂停与合法低帧率另计 |
| 明确连接错误通知 | 收到错误事件即更新本地状态；通道可用时，汇总通知候选目标1秒内 |
| 首次恢复尝试 | 判定需恢复后立即安排，不先等长退避；单次尝试有独立期限 |
| 网络恢复到新鲜画面 | 单独测量重试等待、信令、ICE、关键帧、解码/呈现；初始对照目标可试1-3秒，现场决定验收值 |

对400-1000ms连续波动，画面可以先进入失效提示而会话继续保留；
不应为了“不断开”掩盖不可用画面，也不应把每次抖动都放大为数秒重连。
普通5G无物理冗余时无法保证零中断；若业务要求跨运营商故障仍连续可用，
需要另行立项独立链路/节点与会话切换验证，不能仅靠keepalive或自动重连满足。

### 6.4 强制故障验收

分别断开上传、下行、信令和遥测，测试摄像头停止出帧、ZLM重启、
网络黑洞但socket未关闭、认证过期、浏览器后台/恢复前台、反复短断和长期断网。
每段至少验证：

1. 误判为正常的时间有界，能区分“有连接无新帧”和明确断链。
2. 操作界面及时失效提示，告警不依赖坏掉的连接；断网时不伪称已送达远端。
3. 仅一个重连任务，不泄漏peer、socket、线程或GStreamer分支，不出现同流双发布。
4. 上游恢复后，下游如果保留会话则自动继续，否则自动重新订阅，无需人工刷新。
5. 只有新鲜画面满足条件才报恢复；恢复后不追播旧画面，故障期间数据不从统计中消失。
6. 正常抖动不会触发重连风暴；401/403不会被当作网络故障无限重试。

### 6.5 持续高延迟下的连接保持

持续500-1000ms延迟不单独触发主动销毁会话；传输/反馈仍推进时保持连接并降级，
画面超龄按媒体预算告警。连接可用与画面满足远控要求分别验收。
不能保证无上界延迟、任意丢包或网络黑洞时原连接永不断开。

按配套文档第7节，对上传、下行分别及同时注入500/800/1000ms RTT，
在明确带宽/丢包条件下持续测试，记录误重连、协议/服务端超时与画面状态；
初始建议每组合至少30分钟，属于待确认测试合同。
协议、ZLM或GStreamer引发断开也计入失败，必须定位实际触发层，不能只统计应用主动断开。
保活机制与协议必要检查仍需遵守，不以关闭检查换取表面“不断连”。[S11][S12]

### V6 的测试矩阵与报告

- 正常网络、带宽骤降/恢复、突发丢包/乱序、持续竞争上行。
- 分别注入延迟与短时断网，覆盖400-1000ms量级波动及0.5/1/3秒中断；写明注入方向、
  单向延迟还是RTT、分布与持续时间，不能把 curl 耗时直接作为 netem 单向参数。
- 实际模组切换与实验断网分别留证；信号、小区变化、温度与视频事件统一时间线。
- 车端编码负载、ZLM过载、浏览器解码慢、遥测中断、重连、关键帧突发。
- 上传/下行分别断开、半开连接、ZLM重启、摄像头无帧、认证过期和后台页面；
  按第6节逐段量化检测、通知、恢复，不以最终重新出画面替代过程验收。
- 首先使用同源录像和相同编码约束控制变量，再用动态画面和真实场景验证可辨识性。
  不在同一受限上行无预算地双发两路，避免测出由测试本身造成的拥塞。
- 输出源采集到呈现延迟的p50/p95/p99、画面超龄时间占比、冻结次数/时长/最长时长、
  恢复至实时耗时、实际码率/画质及CPU/GPU/温度；注明时钟误差、测试窗口和缺失项。
- 连续呈现同一旧帧不算“流畅”；无新帧期间应持续计入画面年龄或不可用时长，
  不能只对成功呈现的新帧计算低延迟。
- 验收上限由 V1 确认；通过标准同时约束实时性、可辨识画质和恢复，不只比较平均延迟。

## 8. 生产边界与回退

上传信令、媒体和遥测分别认证并绑定车辆/摄像头/会话；遥测不得携带凭证或视频正文。
策略命令带版本、有效期、序号与执行回执；反馈中断时不能无限重试或排队补执行过期动作。
控制业务流量预留独立预算，视频降级不能把唯一上行全部占满。

播放端区分实时、变旧、冻结、断流，不能让旧画面看起来仍可操作。
画面或指令失效时的车辆处置由车端既有控制/安全系统定义和验收，
不能仅依赖浏览器提示或云端视频服务作最终决定。

保留已验证的 RTSP 配置和软件包。首版切换是受控的会话重建，不声称无缝。
不在运行中盲目自动切换 RTSP/SRT/WebRTC，不让旧、新发布者争用同一个流身份。
回退路径若也超过业务时限，只能报告不可用，不能以“回退成功”代替远控可用。

## 9. 暂不选择的路线与前文纠正

- 不先换掉 ZLM 或重写 Rust 版 go2rtc。若采用 Rust，优先用它实现策略/遥测/管道控制，
  复用 GStreamer 媒体能力；语言选择不替代实时链路验证。
- SRT 可作为允许更大缓冲的传输候选，但不是远控的唯一解；本方案优先验证交互式
  WebRTC 上传，失败时按证据评估其他方案。
- RTSP拉流改RTSP推流，不保证改变底层承载或排队。纯UDP也可能因丢帧和解码依赖冻结，
  不承诺“改UDP绝不卡”。
- `getStatistic`、流量回调或“支持RTCP”不能证明有完整逐流丢包/RTT/反馈接口；
  缺口通过对应commit源码或实测确认，不编造API或GStreamer信号名称。
- 不把未经核实的 `rtc_min_delay_ms` 等配置写进生产；`directProxy`、超时配置也不是
  通用的低延迟开关。
- 随流元数据用于关联，不保证穿过中转和重新打包；不把RTCP RTT当单向或全链路延迟。
- Apollo 官方资料可支持“远程引导与平行驾驶有不同网络要求”的观察，不能据此推断
  萝卜快跑当前生产协议、推拉模式或内部实现。[S10]
