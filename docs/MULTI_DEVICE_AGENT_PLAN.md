## 1. 总体建议

在 mybot 上演进为：

**一个自托管任务与审计中心 + 多个设备执行节点 + 多端控制界面 + 可插拔消息、文档和 App 连接器。**

产品思路可以组合 OpenMausBot 的多 Bot/任务组织和 Cindy 的跨端接续，但不直接拼接两套产品、账号和数据库。重点借鉴 OpenBitFun 的 Rust/TS 和设备连接边界、kojo 的执行归属迁移、QwenPaw 的渠道与扩展协议。

技术路线建议：

- 近期保留现有 FastAPI/SQLite 控制中心，维护一个事实源，不全量重写。
- Rust 优先承担设备常驻、连接、流式转发、文件传输和受控进程管理。
- TypeScript 逐步承担 Web 和连接器；桌面确有原生需求时再评估 Tauri。
- 先实现“手机接着控制同一 Run”，后实现“把执行转到另一台机器”。
- 扩展通过统一协议接入，不要求替换 Agent 核心，不为每个 App 创建另一套会话系统。

如果只选现成产品试用：国内 IM/工具优先评估 QwenPaw；Rust/TS 与设备控制优先评估 OpenBitFun；完整自托管跨端产品优先评估 nanoMuse。这是适配判断，不是本地可靠性或性能排名。

## 3. 七个方案怎么选

以下是 2026-11-07 固定公开快照的观察，不是本地部署测评。完整 commit、已读路径与缺口见开源调研。

| 项目 | 核实与修正 | mybot 的使用方式 |
| --- | --- | --- |
| Cindy | 官方开源页说明公开的是桌面端、手机端和共享 packages；客户端仓库 Apache-2.0，服务端不在该仓库。远程任务在原电脑执行，手机/Pad 负责查看、追问和授权；页面还列出飞书、Slack、GitHub、Jira、MCP、VPC Gateway 等能力。企业自部署 Gateway 属于企业版/候补路径，不能当作当前可直接替换 mybot 的开源服务端。 | 借鉴设备链接、控制端/被控端分离、能力协商、Harness/模型分层和跨端任务连续性；不依赖官方账号/云作为 mybot 核心 |
| nanoMuse | GPL-3.0-or-later；各端与 Relay 有公开源码；自带模型 key 不等于脱离账号/会话服务 | 参考自托管边界与统一渠道接口；代码复制/分发需专项许可评估 |
| kojo | MIT；Go + Web；已有 Hub/Peer 和 Agent device-switch，不只是 CLI 遥控；Windows ConPTY 不具备 POSIX tmux 的服务重启持久性 | 重点研究迁移、执行归属、fencing 与显式降级 |
| QwenPaw | Apache-2.0；Python 核心；渠道、插件、MCP、多 Agent 为公开能力，尚未在本地验证 | 重点研究国内渠道、身份归一化、插件生命周期；不搬整套编排 |
| OpenBitFun | 核心 MIT，Rust + TS；公开 Relay；发布版 LAN/官方连接仍依赖在线身份，私有 Relay 需配套客户端/身份适配 | Rust/TS 与远程能力分层的重点参考，不把它视为现成隔离网络方案 |
| OpenMausBot | Apache-2.0 核心，`enterprise/` 独立 source-available 许可；已有手机配对、同工作区共享会话 | 借鉴多 Bot 和设备撤销；不能说“完全开源全部功能”或“没有跨端上下文” |
| BilldDesk | 所读客户端为 MIT，另有公开 server 等仓库，本轮未审阅；Pro 非开源；开源版警告不建议生产，Linux/iOS 有缺口 | 仅保留人工远程桌面候选，不作为 Agent 中心依赖 |

没有本轮性能基准，不宣称 Rust 产品一定更快，也没有验证手表/眼镜支持。

**不直接 OpenMausBot + Cindy：** 两者各自持有身份、任务、状态、权限和费用事实，直接组合会产生双事实源；Cindy 的公开部分是客户端/共享包，官方远程服务端与企业 Gateway/身份路径不能随客户端直接移植。采用能力思路和受控适配器，不读写上游私有数据库，不依赖未公开 API，不复制 UI。

## 4. 四种跨端能力

| 层次 | 含义 | 顺序 |
| --- | --- | --- |
| 控制端接续 | 电脑、手机、Pad 查看同一 Run，补充输入或审批 | 首期 |
| 内容共享 | 共享持久对话、成果、资料引用、草稿和阅读位置 | 首期从已有服务端内容做起 |
| 执行迁移 | 将后续执行或受支持检查点转移到另一节点 | 后置，需要环境与权限预检 |
| 人工接管 | 看屏幕、键鼠操作、接管 GUI/PTY | 独立高风险能力 |

手机锁屏不等于执行电脑离线。控制端关闭后在线 Node 可以继续；执行电脑休眠时，不能靠同步聊天记录继续原进程，也不能读取其未上传文件。

不保证跨 OS 搬迁活进程、跨 Harness 搬迁内部状态。接力以规范化上下文、检查点和明确的降级结果为准。

## 5. 目标架构

```text
Web / PWA / 后续桌面壳 / 手机与平板
飞书 / 钉钉 / 微信或企业微信 / 邮件入口
                     |
             身份绑定与渠道适配
                     |
          mybot 控制中心：唯一事实源
          项目 / 任务 / Run / Agent
          权限 / 审批 / 用量 / 顺序事件
          Inbox / Outbox / 能力目录 / 调度
              |                  |
       App 连接器与 MCP       设备注册与执行协议
       文档 / 邮箱 / API         |
                            Rust Node
                       Linux / Windows / macOS
                         显式授权的执行器
```

| 层 | 建议分工 | 不做什么 |
| --- | --- | --- |
| 控制中心 | 近期保留 FastAPI；维护状态机、预算、权限、审计 | 不让两套调度器控制同一 Run |
| Node | Rust；异步 I/O 可评估 Tokio，有入站 HTTP 需要时再评估 Axum | 不默认开放高权限公网端口，不把语言安全当 OS 沙箱 |
| 界面 | 现有原创 Web 渐进 TS 化；先浏览器/PWA，原生需求再评估 Tauri 2 | 不先换框架或复制上游布局，不删设计历史 |
| 连接器 | TS 优先，官方 SDK，独立受限进程 | 进程分离不是完整沙箱，不共享全部凭证/目录 |
| 工具协议 | 内部版本化 schema，受控 MCP 适配 | MCP 不等于鉴权、沙箱或运行迁移 |
| Harness 执行适配 | Codex、Pi、DeepSeek Harness 以相同能力/事件/权限契约比较 | 一个 Run 不叠加多个主循环，不默认导入彼此凭证 |
| 客户端参考 | 研究 HuLa 的 Tauri/平台/消息边界，维持原创体验 | 不复制聊天 UI，不将上游暂不支持的 Web 当作已覆盖 |
| 存储 | 单人单写 SQLite；成果先用私有目录 | 不同步 SQLite/WAL 文件；需求明确后再评估 PostgreSQL |

预留逻辑边界 `protocols`、`device-node`、`connectors`、`policy`，本轮不创建空工程。以 JSON Schema/OpenAPI 与契约测试生成 TS/Rust 类型，不同时引入多套等价通信协议。

网络先考虑私网/VPN + HTTPS，但网络身份不替代应用权限；不强制 Tailscale，也不承诺永远直连，Tailscale 可能使用 Peer Relay/DERP。有实际跨网需求再建设 Relay。

控制中心需要读取被授权资料来调度模型，不能宣称整体中心不可见。若后续使用盲转发 Relay，只对相应设备链路采用成熟加密实现，不自创密码协议；IM、邮箱、文档、模型各有独立数据边界。自托管不等于使用 SaaS 时数据不离开内网。

## 6. 状态、命令与迁移

### 6.1 建议新增对象

- `Principal/Membership/Device`：人或服务身份、项目权限、控制端/执行节点。
- `AgentProfile`：长期角色和能力模板，与单次 Run 里的 Agent 实例区分。
- `ThreadBinding`：渠道安装、租户、账号、话题与项目/任务映射。
- `Command`：ID、发起身份/设备、目标、预期状态版本、预算确认和结果。
- `ExecutionLease`：节点、到期时间、递增 fencing token，旧节点恢复后不能继续成为写入权威。
- `ContextBundle`：资料引用/hash、规范化上下文、计划版本、工具未决状态、兼容版本。
- `Connection/CapabilityGrant/Approval/OperationReceipt`：连接、授权、一次动作确认与回执。

### 6.2 同步与控制

服务端快照 + 顺序事件 + 客户端游标；先用 SSE 或增量 HTTP，同步命令走 HTTPS，高频双向 PTY/屏幕另用 WebSocket。订阅处理快照水位竞态，过期游标重建快照，客户端按事件 ID 去重。

所有事件按项目权限过滤，不能从全局 `seq` 读取其他项目。多端可同时观察/发出语义命令，由状态版本/CAS 处理冲突；GUI/PTY 键鼠输入才需要独占可撤销控制权，且与 Worker 执行租约分开。

草稿先做版本冲突提示，阅读位置按人/设备保存，不在首期引入全量 CRDT。暂停、取消、恢复继承执行器真实语义；当前仍是阶段边界暂停，取消不是撤销，也不保证 Provider 停止计费。

### 6.3 执行迁移

```text
目标预检 -> 源节点收敛 -> 检查点/未决动作持久化
         -> 授权内容传输与 hash 校验
         -> 中心原子转移归属/fencing
         -> 目标确认接管 -> 源节点退出或失权
```

源离线、环境不兼容、工具无检查点或存在未决副作用时，排队、拒绝或由人确认新尝试，不假装无缝。凭证默认不随内容包迁移，应重新授权或使用受限代理。

租约不能阻止已发出的外部请求。发信、写文档等通过供应商幂等键或回执查询处理；结果无法确定时标记 `outcome_unknown`，不自动重发。不承诺跨系统副作用“恰好一次”。

## 7. 可扩展能力系统

| 类型 | 职责 | 例子 |
| --- | --- | --- |
| Channel | 收发消息、话题映射、控制入口 | 飞书、钉钉、微信、邮件入口 |
| Resource | 读取、检索授权资料 | 语雀、飞书文档、邮件、Git 文本 |
| Action | 业务副作用 | 发信、写文档、建工单 |
| Executor | 某节点上的受控工作 | 只读研究、后续编码/浏览器/OS 操作 |
| Model Provider | 模型协议与能力声明 | 现有 Chat Completions 与后续适配 |
| Trigger | 授权事件提出工作 | Webhook、定时、文档变化 |

Skill/工作流是能力组合，不是提权方式。新增 App 应能独立安装、配置、授权、测试、停用、撤销、卸载，不要求修改核心编排。

扩展必须声明版本/hash、来源/许可证、配置与输入输出 schema、资源范围、scopes、网络/目录限制、读写等级、超时/并发/载荷上限、幂等与重试分类、日志脱敏、凭证引用、审批和数据保留策略。

宿主提供 `configure/start/health/stop/revoke/list_capabilities/invoke` 等受限接口。声明本身不可信，执行时由宿主强制收紧；新增工具、扩大 scope 或域名必须重新审查。保存配置、建立连接和真实业务测试分别记录，不以“在线”覆盖全部。

**App 接入优先级：** 官方 API/SDK -> 审阅过的 MCP -> 官方 CLI/Deep Link/文件交换 -> 授权浏览器执行器 -> OS 自动化/人工远程桌面。不承诺任意 App 都可控制，不绕过验证码和系统授权。

## 8. 首批应用能力

下表全部是计划，mybot 尚未实际接通。

| 应用 | 首批范围 | 后续 | 边界 |
| --- | --- | --- | --- |
| 飞书 | 查询、脱敏通知、任务草稿、Web 深链接 | 文档只读、审批卡片、确认写回 | 官方 SDK 有 WebSocket 事件通道；具体事件、租户/权限逐项验收 |
| 钉钉 | 机器人对话、查询/通知/任务草稿 | 交互审批、文档/日程等独立 API | Stream 机器人接收与只发通知的群 Webhook 区分 |
| 企业微信 | 企业应用/机器人消息入口 | 按公开接口扩展 | 内部消息、客户联系、群机器人不是同一权限 |
| 微信 | 评估腾讯官方通道的扫码、配对、收发 | 官方允许的媒体等范围 | `openclaw-weixin` 当前是 OpenClaw 插件，不是 mybot 即插即用；不承诺全历史/联系人/朋友圈/任意群 |
| 语雀 | 指定知识库搜索/读取、来源引用 | 草稿，经确认创建/更新 | 官方 MCP 为 MIT；token 可能有写权，首期只暴露读工具；附件/成员管理不作已支持 |
| 邮箱 | 指定范围检索/阅读/摘要/回复草稿 | 确认发信、附件/日程 | Gmail/Graph API/OAuth 与 IMAP/SMTP 分别适配，读和发送分权；不默认收全邮箱 |
| 其他 App | 复用能力协议 | GitHub/GitLab、日历、网盘、工单等 | 增加连接器不等于自动授权 |

微信已出现腾讯公开官方通道候选，不能沿用“个人微信只能非官方机器人”的旧前提；也不能把客户端协议字段当成完整服务端契约。默认不采用个人号 Hook 或来源不明插件。

### 8.1 统一处理链

```text
事件 -> 签名/连接身份/时效验证 -> 持久 Inbox 去重
     -> 账号/租户/用户/话题映射 -> 项目权限
     -> 显式命令或待确认任务 -> 资料发送/预算确认
     -> Run/审批/成果 -> Outbox -> 供应商回执
```

去重键包含供应商、安装、账号/租户和事件 ID。跨渠道身份主动绑定，不凭昵称或邮箱相同自动合并；邮件 `From` 也不能作为控制身份。

首期外部消息只查询、通知和建立草稿。模型费用/资料外发仍回 Web 明确确认；后续 IM 内确认必须具备等价预览和一次性动作绑定，不把任意“好的”当批准。

通知也有副作用，预先批准目标和内容策略；默认只发脱敏状态与重新鉴权的链接，不回显完整代码、文档、邮件或秘密到群里。

### 8.2 文档与邮件

外部正文是资料，不是系统指令。首次按需读取，不先爬全库；实际送模型的片段进入确认快照。索引/缓存绑定来源、版本和 ACL，授权撤销后同时阻断缓存访问。

附件限制大小、格式、路径和解压比例，受限解析，不加载邮件远程图片/主动内容。发信/写文档展示目标、内容差异、附件/权限变化；批准绑定动作 hash、操作者和有效期，内容变更重新确认。未知结果不补发。

## 9. 平台矩阵

| 平台 | 控制端 | 执行节点规划 | 不承诺 |
| --- | --- | --- | --- |
| Linux | Web/PWA，后续桌面壳 | 首个 Rust Node | X11/Wayland 权限等价 |
| Windows | Web，后续桌面壳 | 原生 Node，路径/ACL/进程树/ConPTY 专验 | 当前 Python 服务端因此可用；WSL 等于原生 |
| macOS | Web，后续桌面壳 | 后续 Node，签名/系统权限专验 | 复用 Linux 隔离假设 |
| Android/Pad | 先 Web/PWA，必要时原生壳 | App/OS 操作独立实验 | 后台常驻、任意 App 控制、所有省电策略兼容 |
| iPhone/iPad | Safari/Web/PWA，后续按需通知/壳 | 默认仅控制端，执行在在线电脑/服务器 | 任意控制其他 App、持续后台 Agent |
| 其他平板/折叠屏 | 按引擎、触摸、键盘、分屏测试 | 按实际 OS 决定 | 尺寸模拟等于真机兼容 |
| 手表/眼镜 | 后续状态/有限审批候选 | 不在首批 | Rust 能编译等于产品可用 |

PWA 不是离线执行保证。推送只提醒，点击后重新获取已鉴权状态；不在通知载荷放敏感正文。

## 10. 性能与验收

先测量增量同步、分页、长列表、连接复用、有界队列、背压、慢客户端、内存和 CPU。Rust 优先放在常驻/传输/进程热点，不用语言替换掩盖模型和网络延迟。

建议固定硬件/版本，用测试 Provider，10,000 条事件、10 个控制端、2 个 Node，在本机/受控延迟/断线条件分别测量。以下为候选目标，未测试、未承诺：

| 指标 | 候选目标与口径 |
| --- | --- |
| 命令接收持久化 | 服务端 p95 < 200 ms，不含供应商调用 |
| 多端事件可见 | 正常网络 p95 < 1 s |
| 重连 | 网络恢复 5 s 内开始补齐；丢事件为 0，重复可去重 |
| 长记录 | 10,000 事件分页可用；新增事件不全量重绘 |
| 常驻成本 | 实测 Node RSS/CPU/吞吐后设预算，不编造节省比例 |

只有控制中心成为实测瓶颈或确需统一打包时，再提出 Rust 控制中心 ADR；用明确迁移、停写切换、历史对照和回滚，不双写同库。

## 11. 分期计划

这是依赖顺序，不是工期承诺；原有真实 Provider、Safari/真机缺口仍保留。

| 阶段 | 交付 | 验收门槛 |
| --- | --- | --- |
| S0 | 身份/权限、设备/命令/扩展协议与威胁模型 | 契约评审；不接真实账号 |
| S1 | 同一人电脑/手机/Pad 控制同一 Run、设备撤销、增量同步 | 断线/锁屏/冲突/事件补齐，不改变暂停和费用语义 |
| S2 | 飞书或钉钉一个渠道，加语雀只读 | 先夹具后授权真实账号；去重/越权/撤销/敏感输出 |
| S3 | Linux Rust Node，再 Windows | 配对/心跳/单一执行归属/重启/路径与资源限额 |
| S4 | 另一 IM、企微/微信官方通道、邮箱只读与草稿 | 逐渠道往返证据、账号隔离、scope 和状态分层 |
| S5 | 文档写回/发信；编码/浏览器/桌面另立执行授权 | 动作审批/回执/未知结果不重放；OS 隔离专项 |
| S6 | 支持的检查点迁移、项目成员/团队控制 | 分区/旧节点恢复/fencing/跨 OS 降级/凭证隔离 |

首期不做集群、插件市场、完整 CRDT、自研远程桌面或穿戴客户端。实现前需确认单人多端还是多人、常在线中心、私网或公网入口、首个 IM/邮箱类型、是否要求独立身份与离线登录。

### OpenMausBot 先行但不替换底座

先行验证的理由是它同时覆盖本地 Agent、审批、手机配对、连接应用和自托管，能较快暴露真正的产品边界。但它当前固定源码的默认审批级别是 `full`，Bot API 又明确禁用 Shell、Computer、Browser、Connected Apps 和 MCP，因此“能启动/能聊天”不能证明它适合作为 mybot 的执行内核。

先跑隔离的 P0/P1 验收；通过后以适配器接入 mybot，失败则保留为参考。不要让 Cindy、nanoMuse、QwenPaw 的云/Relay/数据库与 OpenMausBot 同时成为事实源。模块级来源和采用/淘汰记录见 `OPEN_SOURCE_ADOPTION_MAP.md`。

推荐下一步：先评审 S0/S1，再实施单人多端控制；每个模块按配套台账推进“来源 -> 机制 -> 本地设计 -> 测试 -> 决策”，不把研究结论升级成已实现。

## 12. 持续迭代

`OPEN_SOURCE_ADOPTION_MAP.md` 给每个模块固定 M01-M19 标识和下一轮验证；原四项目及新增 Pi/DeepSeek Harness/HuLa 的 REA 工具链见 `REA_PROJECT_BREAKDOWNS.md` 及其子文档。每轮保留版本/差异，重大技术变化经 ADR 确认；UI 反馈另写 `UI_ITERATIONS.md`，不混成安全/业务验收。

必测：重复入站不重复运行；双端操作幂等/冲突；旧 Node 恢复不双执行；写请求超时不盲目补发；撤销阻断旧连接与缓存；提示注入不能提权；第三方断连不阻塞核心任务。

## 13. Cindy 官方开源边界核对

2026-11-07 查阅官方开源页 [cindy.cn/#open-source](https://cindy.cn/#open-source)：

- 页面将开源范围描述为桌面端、手机端和共享 packages；客户端代码以 Apache-2.0 为主。
- 页面明确说明服务端位于独立仓库、不是客户端 monorepo 的内容；远程访问需要登录同一账号、相关电脑在线并开启相应权限。
- 页面列出飞书、Slack、GitHub、Jira、MCP、本地模型和 VPC Gateway 等连接能力，但能力是否可用取决于版本、账号、授权和服务配置。
- 企业 Gateway 以企业版/候补路径提供“自部署或官方托管”选项；这不等于当前 Apache-2.0 客户端仓库包含可直接部署的完整服务端、身份系统或离线模式。
- 页面还明确区分“项目文件留在原电脑”和“云端同步的对话、记忆、Skill、附件”；这不等于跨设备复制整个工作区。

因此本方案把 Cindy 放在 M04/M05 设备协议、Harness/模型分层和连接器入口借鉴位，不放在控制中心、事实源或私有 Relay 底座位。上述页面没有替代固定 commit 的源码证据，也没有构成 mybot 的运行验收。
