# 研发团队 AI 工作台：产品基线

更新日期：2026-11-01。

状态：用户最新明确面向研发团队，先单人试点；原创界面、可追踪、可视化和便于分析是核心要求。能力细节、界面方案及技术选型仍待评审。最新定位见 [ADR-0002](decisions/ADR-0002-rnd-team-single-user-pilot.md)，它修订了 ADR-0001 中的“个人产品”定位。

## 1. 产品定义

让研发人员与团队能够在项目上下文中，指挥多个模型和 Agent 完成工作，并依据真实执行证据协作、审查、追踪和改进。

“先个人”表示先用一名研发人员验证完整体验，不表示长期做通用个人助手；“面向团队”也不表示首版立即建设完整企业平台。

```text
表达目标 -> 确认计划 -> 组织执行 -> 检查证据与成果 -> 分析与改进
```

对话是输入方式，项目是上下文容器，任务是工作单元，运行是一次执行尝试，成果是可交付结果。

工作台不等于聊天记录、模型目录、Agent 群聊、流程画布、MLOps 平台或 CI/CD 平台中的任何一个。它把必要能力组合成可控的研发工作体验，不要求所有工作走完整交付流水线。

## 2. 已确认与待评审

| 类别 | 内容 |
| --- | --- |
| 已确认 | 产品面向研发团队，先单人试点；界面完全原创 |
| 已确认 | 支持 Super-agent/Subagent 与合适模型分工 |

用户对方向的确认不等于对某一框架、视觉稿或全部能力的验收。

## 3. 能力边界

核心能力为：

1. 目标和项目上下文。
2. 任务计划与受限委派。
3. 模型、工具和环境连接。
4. 可观察、可控制的执行。
5. 全链路追踪和审计。
6. 成果、版本和验证证据。
7. 运行分析、比较和经验复用。

分期和用户价值详见 [CAPABILITY_MAP.md](CAPABILITY_MAP.md)。

GPU 环境、模型运行时、推理服务和实验管理保留在完整愿景中，但不是使用工作台的前提。远程模型用户无需安装本地 GPU 栈。

## 4. Super-agent、Subagent 与调度器

| 对象 | 职责 |
| --- | --- |
| Super-agent | 理解目标，提出计划、委派和结果汇总建议 |
| Subagent | 在限定上下文、工具和预算内完成专业子任务 |
| 模型 | 为一次或多次 Agent 决策提供推理，不等于角色本身 |
| 调度器 | 检查依赖、权限、资源和预算，实际安排任务执行 |
| Worker | 在受控环境运行工具、代码、测试或浏览器 |

Super-agent 不能用自然语言绕过调度器的授权。首版简单任务可直接完成；复杂任务才委派，不要求七个角色常驻。

初始限制提案：一个协调者、最多两个并行 Subagent、子 Agent 不递归委派、同一代码工作区一个写入者。限制在 POC 验证后可调整。

## 5. 最小架构方向

```text
原创 Web 工作台
      |
项目 / 任务 / 成果 / 授权服务
      |
持久化任务调度器 ---- 受控执行 Worker
      |                     |
事件与审计记录         模型 / 工具 / 环境适配器
      |
追踪投影 / 图 / 时间线 / 分析
```

优先一个应用服务、一个 Worker、一种元数据存储和本地成果存储。先验证一种编排方式，不默认同时引入多个框架。

事件记录负责还原状态；追踪用于定位调用链和性能。具体协议、数据库、前端框架及遥测库仍是候选，不因为本地项目使用某框架就继承它。

## 6. 工具与外部服务

- 模型连接不绑定单一提供商，也不默认任何 API 无限免费。
- 工具授权限定项目、目录、账户和操作，凭证不进入普通日志。
- 现有项目仅作能力候选，不决定 UI。
- 工作成果由工作台组织；镜像、包等发布制品可后续接入 Artifact Keeper。
- Mattermost 是可选通知渠道，不是单人试点的启动前提。

共享服务上线前必须具备用户身份、项目访问控制、凭证范围和审批责任记录；可以后置复杂组织管理和 SSO，不能后置基本隔离。

阅读与验证边界见 [REFERENCE_AUDIT.md](REFERENCE_AUDIT.md)。

## 7. 界面原则

- 先看懂正在做的工作，再按需查看调度和调用细节。
- 对话、计划、执行、成果相互关联，不分裂成多个独立工具。
- 图、树、时间线、表格分别解决不同问题，不堆在一张图中。
- 使用同一运行数据驱动所有视图，图节点不是动画模拟状态。
- 可查证摘要和工具证据可见，模型内部思维链不作为产品展示内容。
- 原创视觉、布局和交互，不借鉴 `/home/my/workspace/ainfra` 下的项目。

具体方案见 [UI_DESIGN.md](UI_DESIGN.md) 和 [VISUAL_SCHEDULING.md](VISUAL_SCHEDULING.md)。

## 8. 验证与阶段

先设计六条旅程：首次进入、创建项目、发起任务、查看成果、审批、失败接管。

首批 POC 分别验证：

- 调研出方案：没有仓库和 GPU 也能完成。
- 修改代码并测试：限定仓库、隔离变更、真实测试、人工决定是否应用。

构建部署、运维、GPU/模型实验和复杂组织能力后置；开启共享项目时必须先具备基本身份和访问隔离。首版成功不以 Agent 数量为标准，而以结果可用、过程可查、动作可控、失败可解释为标准。

旧 `prototype/` 保留但未采用，不作为实现起点。当前只开展设计，详细门槛见 [EXECUTION_PLAN.md](EXECUTION_PLAN.md) 和 [DESIGN_REVIEW.md](DESIGN_REVIEW.md)。
