# 远控视频：自顶向下可观测性与落地任务拆解

状态：设计与待办，未接入车辆/ZLM、未采集现场数据、未完成以下验收。
配套[最终方案](REMOTE_VIDEO_ADAPTATION_PLAN.md)，用于先诊断当前RTSP链路，
再验证WebRTC主动上传。本文不把协议迁移当作观测能力的前提。
可落地性修正：S0-S8是分析边界，不意味着现场能拿到每段全部指标。
首版范围、权限前提和缺失时的合并定位规则，以第2.1-2.4节为准；完整逐帧追踪不是开工前提。

## 1. 顶层目标与交付

发生延迟、冻结、断链时，应回答：

1. 哪辆车、哪个摄像头、哪个操作席、哪个会话受影响？
2. 是连接失效、仍有连接但无新帧，还是帧持续到达但画面过旧？
3. 最后一个正常边界、首个异常边界在哪里？双向媒体/反馈哪一侧异常？
4. 结论是已定位、疑似还是未知？有哪些同窗口证据与相反证据？
5. 当前执行什么恢复动作、由谁负责、什么时候下一次检查？
6. 何时收到新鲜画面、何时恢复稳定？是否发生误断连或重连风暴？

最终交付是：真实拓扑、分段探针、统一数据字典、故障时间线、定位规则、恢复状态机、
故障注入及证据报告。不能用一张“总RTT/总丢包”图代替。

### 自顶向下四层

| 层级 | 呈现内容 | 下钻结果 |
| --- | --- | --- |
| L0 业务可用性 | 画面年龄、冻结、可辨识质量、不可用时长、连接/恢复状态 | 选择受影响车辆/摄像头/操作席 |
| L1 真实链路 | 各段健康、延迟增长位置、观测缺口、实际承载与路径变更 | 选择异常段与故障窗口 |
| L2 分段指标 | 同时间窗的收发速率、队列、RTT、重传/丢包、帧进展、系统负载 | 选择连接/帧/事件证据 |
| L3 证据与动作 | 原始事件、指标口径、时钟误差、定位结论、恢复尝试/回执 | 复现故障与验证恢复 |

L0把“传输连接仍在”和“实时画面可用”分开显示；存在未知关键段时不宣布全链路健康。
报警与自动调参、重连分别留事件，便于识别是否由策略自身造成卡顿。

## 2. 按实际边界拆段

```text
S0 摄像头/ROS2采集
 -> S1 GStreamer原始队列/编码
 -> S2 车端socket/内核队列/网卡/模组接入
 -> S3 5G空口/运营商/VPN/WAN上传区间
 -> S4 云端实际入口/中转/内核socket接收
 -> S5 ZLM解包/缓存/转发调度
 -> S6 云端出口/中转/WAN下行区间
 -> S7 播放设备本地网络/PeerConnection接收
 -> S8 抖动缓冲/解码/呈现

C0 信令与认证：单独记录建连请求与会话生命周期
C1 遥测与事件：单独记录上报延迟、缺失、补齐与数据新鲜度
```

这是一份边界模板。V0/O0必须填入现场实际经过的网关、VPN、NAT、TURN、
负载均衡及接口；不存在的节点标为不适用，不能凭图认定有这些设备。
当前RTSP拉流与未来WebRTC上传保留同一分段ID，记录不同会话类型和恢复责任方。
如车内还有一次RTSP桥接，为该连接建立独立子段与时间戳，避免把本地耗时记到5G上。

| 段 | 目标观测证据（非首版全部必采） | 责任范围与可以定位到的边界 |
| --- | --- | --- |
| S0 采集 | 源帧号/采集时间、源帧率、发布/订阅进度、实际ROS2队列策略 | 摄像头/ROS2；源无新帧不归因WAN |
| S1 编码 | 编码输入/输出时间、实际码率、queue驻留、关键帧、错误/EOS | 车端媒体；区分源停、编码慢与编码后积压 |
| S2 车端发送 | 同流socket统计、内核排队、qdisc、网卡错误/丢弃、模组连接状态 | 车端OS/网关/模组；应用send成功不是已越过5G |
| S3 上传区间 | 车端与云端边界同流收发、上传RTT/反馈、模组事件、VPN/中转路径 | 网络团队；无中间探针只能定位上传区间，不能精确指认某基站/运营商路由 |
| S4 云端接收 | 实际接入协议、NIC入包、socket接收/丢弃、接收队列、入口策略变更 | 云平台/主机；NIC已收到但应用晚取要检查本机接收与调度 |
| S5 ZLM处理 | 收包到成帧/转发的关联、缓存驻留、输入输出速率、线程/CPU、会话事件 | ZLM维护方；API缺字段时记录缺口，必要时增加该commit的最小探针 |
| S6 下行区间 | ZLM出流与接收端统计、下行反馈、实际候选路径、云端出口队列 | 分发/网络；单个观看者故障不默认归因车辆上传 |
| S7 播放端接收 | 收包/帧进展、连接状态、候选对、可取得的本机网络统计 | 播放器/客户端；普通浏览器无法保证提供网卡/系统队列明细 |
| S8 解码呈现 | 缓冲窗口均值、完整帧/解码/呈现进展、丢帧、冻结、页面可见性 | 播放器；收包在推进但不呈现，优先检查媒体完整性/解码/渲染 |
| C0 信令 | DNS/建连/TLS/请求时长、状态码、会话建立与销毁原因 | 接入管理；不把HTTP时长当作媒体单向时延 |
| C1 遥测 | 本地采集时间、接收时间、序号缺口、队列深度、时钟质量 | 观测服务；上报晚到不等于当时媒体晚到 |

### 2.1 可获得性分级，优先于理想指标清单

前文“必采/需要观测”不能理解为默认已经存在这些接口。每个字段都先建能力记录：
来源、现场版本、权限、实测样例、单位/语义、是否随实际流量变化、不可用原因。
在现场核验前，状态统一为 `unverified`，不能仅凭文档标为 `available`。

| 实现级别 | 含义 | 首版处理 |
| --- | --- | --- |
| A 公开接口候选 | 浏览器API、已部署服务API或可读系统计数 | 先试现有接口；仍需实际权限、版本和字段验证 |
| B 小范围应用埋点 | 能修改车端应用或播放器，增加计数/时间/事件 | 可作为首版建设内容，先确认代码所有权 |
| C 专门适配 | 修改ZLM、获取内核/驱动权限、对接厂商模组接口 | 不默认阻塞首版；缺口确实影响诊断时单独做 |
| D 不在控制范围 | 运营商内部队列、真实空口调度、不可访问中间节点 | 首版不承诺取得；只保留合并网络区间和辅助证据 |

这是实施路径分级，不代表成功率或已确认能力，也不承诺未验证的开发周期。
能力检测失败分别标明 `unsupported`、`forbidden`、`error`、`stale`；
权限不足不能当作不支持，也不能自动申请高权限或升级版本。

### 2.2 逐段难点与首版落地办法

| 段 / 相对难度 | 主要难点 | 首版最小实施路径 | 拿不到时的降级边界 |
| --- | --- | --- | --- |
| S0 采集：中，B | ROS时间戳不一定来自曝光时刻，摄像头/驱动未开放细节 | 在已有订阅/接入回调记录接收计数和本机单调时间；有可靠源时间戳才另存 | 只称“应用收到帧”，合并摄像头到接入之间的耗时，不报真实采集延迟 |
| S1 编码：中，B | 硬编异步、buffer不一定是一帧、PTS可能被改变 | 应用中在编码器前后加非阻塞pad probe，记录进度/字节/PTS与bus错误，适配访问单元边界[S17] | 无法匹配输入输出时仅报两侧进展；不能修改gst-launch宿主时先做进程存活/错误日志，标明缺媒体进展 |
| S2 车端发送：中到高，A/C | fd归属、容器/命名空间、TCP/UDP统计差异，socket不一定由应用持有 | 先核验能读的接口总量、错误、qdisc及同连接TCP统计；与S1输出同窗并列 | 无权限则保留应用输出与远端输入，合并S2-S4；不假报每流排队/空口发包时间 |
| S3 5G/WAN上传：高，A/C/D | 中间网络不可控；模组管理口可能未开放，切换事件不可靠 | 用车端输出与云端输入划边界，采集可用RTT/重传；信号/小区/温度仅在厂商接口已核实时接入 | 定位“车端应用输出到云端收流之间”，不精确指认基站、运营商队列或单向网络耗时 |
| S4 云端接收：中，A/C | NIC总量不是逐流数据，NIC到socket/应用之间可能缺采样点 | 先读主机负载/接口计数，使用经核验的ZLM输入进展；必要时按活动连接短时采样 | 缺socket/内核探针就合并S3/S4，不把收到接口流量等同该视频已到达应用 |
| S5 ZLM内部：高，A/C | HTTP接口不保证提供逐帧时序、逐观看者出流及内部队列 | 先核验getMediaList等现有接口字段；流注册/轨道存在仅证明存在。确需更细时对固定commit增加输入、每观看者输出两个最小探针[S5] | 不能改ZLM则先保留“ZLM入口之后到浏览器之前”的合并区间；不声称已分开转发与下行耗时 |
| S6 下行网络：中到高，A/C/D | 服务端实际发送边界可能缺失；浏览器反馈只代表该连接 | 以该观看者候选对/接收统计观察下行现象，能取ZLM逐peer输出时再做两端对照 | 没有服务端输出证据，报告“S5-S7区间异常”，不单凭浏览器丢包判定公网问题 |
| S7 浏览器接收：低到中，A/B | 字段因浏览器/连接状态变化，无法从网页取得完整NIC/无线信息 | 对实际PeerConnection调用getStats，按能力采集收包字节/包、候选对与连接事件[S7] | 无RTT/丢包字段不补0；仅保留可确认进展。不能访问PeerConnection则需播放器适配 |
| S8 解码呈现：中，A/B | 标准冻结字段可能缺失、后台限频、源时间戳不透传 | 使用可用的framesDecoded/呈现进度加本地看门狗；保留可见性与媒体事件 | 只报告“本地播放进展停滞”，不宣称精确玻璃到玻璃延迟；无呈现接口时说明仅测到解码 |
| C0/C1 信令/遥测：低到中，B | 重连、鉴权、乱序、上报阻塞可能混入媒体故障 | 在自有请求/连接管理器记录状态、耗时、序号、超时与恢复事件 | 取不到服务端内部时序就只报客户端请求总耗时；遥测断开后保留本地有界事件 |

S5的两个探针先只记：连接/会话epoch、流/观看者身份、字节/媒体单元计数、
最后进展单调时间及关闭原因；不在首版强制全帧号透传。
探针的“输出”是明确的应用提交边界，不等于已经从网卡发出。
pad probe只更新内存计数并快速返回，异步导出；不能在流线程执行HTTP或阻塞写日志。
PTS只在验证过对应关系后用于同管道阶段关联，不能当作跨ZLM的全局帧ID。

### 2.3 首版真正依赖什么

首版先建设以下数据，不要求先接入信号强度、基站ID、硬件时间戳、eBPF或全链路帧ID：

| 观测点 | 要求 | 取数前提 / 失败处理 |
| --- | --- | --- |
| M0 车端输出 | 至少一个能反映实际编码产出的计数及最后进展时间 | 允许在车端应用加埋点；只有进程存活不够，缺少时如实降低诊断等级 |
| M1 ZLM输入 | 逐流输入媒体进展 | 现有API字段实测可用则复用；否则需要最小服务端探针，做不到就保留该边界未知 |
| M2 ZLM逐观看者输出 | 每个实际播放会话的输出进展和状态 | 增强项；API不具备则需补探针，暂缺时合并ZLM与下行 |
| M3 浏览器 | 实际收包进展与解码/呈现进展、连接事件 | 允许适配自有播放器；字段缺失时使用能确认的计数/事件并标明口径 |
| M4 关联 | 相同逻辑流、会话/节点启动ID、采集时间/窗口和数据新鲜度 | 首版不要求跨机绝对时间精准，但禁止用未同步时钟相减得到单向延迟 |

ZLM当前官方文档中，getMediaList示例包含bytesSpeed、轨道frames等；
不能推定getMediaInfo等其他接口或2025年构建提供相同字段，更不能把接口名称当成进展指标。
API存在也不保证2025年构建具有相同字段；应验证业务code、完整结构和真实样例。
测试源停顿、恢复及重连时字段是否如预期变化，排除静态fps/缓存在线状态等假进展。[S5]

逐帧端到端延迟另列增强项：需要源时间戳、跨机时间质量和明确帧映射。
它未实现时仍能做停流和范围定位，但不能声称已经测得各段精确毫秒延迟。

### 2.4 拿到多少证据，就输出多细的结论

| 已验证的边界 | 允许报告的粒度 | 仍不能承诺 |
| --- | --- | --- |
| 只有M3 | 浏览器是否收包、是否解码/呈现推进 | 区分车端、上传、ZLM和下行根因 |
| M0 + M3 | 车端产出停滞，或两端之间/播放器问题 | 把中间区间进一步归为5G或ZLM |
| M0 + M1 + M3 | 车端产出、车端输出到ZLM输入、ZLM输入之后到浏览器 | 缺M2时独立指认ZLM转发或下行 |
| M0 + M1 + M2 + M3 | 车端、上传区间、ZLM处理区间、对应观看者下行区间及播放器 | 精确定位无探针的运营商内部节点 |
| 再有内核/接口/模组探针 | 按实际证据继续细分本机队列/丢弃与网络区间 | 软件发送时间戳等同无线真实发送时刻 |

任何“输入到输出”结论都要确认实际观测点语义与对应关系；
只看到字节计数增加不证明是相同源帧，也不直接证明画面新鲜。
首版诊断报告必须显示当前边界覆盖度，避免把合并区间显示成已精确定位。

### 2.5 按ROS2/GStreamer/ZLM/WebRTC核对确定能力

这里“确定可做”指有明确公开接口，或可通过自有应用增加小范围代码实现，
不等于用户现场已经接通。前提是允许修改相应车端应用/播放器，或能够读取ZLM管理接口。
缺少这些权限时仍需降级；不能把“原则上可开发”写成“现场已支持”。

| 组件 | 确定的实现入口 | 能落地的观测 | 不能直接保证 |
| --- | --- | --- | --- |
| ROS2接入，B | 自有订阅回调 + 单调时钟 + 应用计数器[S18] | 收到消息总数、窗口到达频率、最后收到时间、回调开始/结束耗时；配合定时器识别无消息 | 曝光到接收延迟、DDS真实丢包率、发布者内部排队或驱动原因 |
| ROS2消息字段，A/B | 实际消息类型；Image/Header定义[S19][S20] | 读取存在的header.stamp与图像属性；独立记录本机接收时间 | stamp一定正确同步；frame_id是逐帧序号 |
| GStreamer编码路径，B | 编码器前后非阻塞pad probe[S17] | 各边界buffer/字节进展、最后进展时间、可读PTS；验证访问单元后才命名为视频帧数 | 一个buffer等于一帧；硬编输入输出一一对应；PTS跨ZLM不变 |
| GStreamer队列，A/B | 实际queue元素current-level-buffers/bytes/time[S9] | 明确该queue当前积压的buffer数、字节量和媒体时长 | 所有插件/内核内部队列都可读；current-level-time等于真实墙钟驻留时间 |
| GStreamer生命周期，B | bus的ERROR、EOS、STATE_CHANGED[S22] | 收集已发布的错误/结束/状态变化，关联管道实例与恢复动作 | 每次网络黑洞都立即发ERROR；所以仍需媒体进展看门狗 |
| ZLM流管理，A | 当前官方API中的getMediaList等[S5] | 按流筛选、核实存在/轨道/观看人数，以及实际版本提供的进展字段 | HTTP200等于成功；在线或ready等于持续出帧；全局流量等于逐流流量 |
| ZLM输入进展，A/C | 当前文档getMediaList的bytesSpeed/tracks.frames候选；无字段时补探针[S5] | 字段经停源/恢复实测后，按视频轨道记录累计量/增量和流重建 | 2025年构建必有同样字段；统计更新频率足够亚秒检测 |
| ZLM拉流恢复，A/C | 当前固定源码PlayerProxy的失败/关闭回调与rePlay调度[S23] | 复用已有重拉责任方，记录断开、等待、重试、重连结果；现场先核对相应代码/日志 | 用户2025年默认等待、回调、保留下游方式与本次2026年快照相同 |
| ZLM逐peer输出/内部耗时，C | 对现场固定commit寻找输出边界，增加有界计数/时间探针 | 有代码权限时可开发逐观看者提交进度及关闭原因，先不做全链路帧映射 | 有通用HTTP接口直接提供逐包排队/真实出网时间；不改源码就能取得全部细节 |
| 浏览器连接，A/B | 自有播放器的RTCPeerConnection状态/ICE事件[S11] | 连接状态变化、本地失效提示、受控重新信令建连与会话epoch隔离 | 所有失败即时检测；只用restartIce就兼容所有ZLM；网络永不断连 |
| 浏览器接收/解码，A/B | 实际PeerConnection.getStats()[S7] | 逐字段核验后读取bytesReceived/packetsReceived/framesDecoded等，按窗口求增量 | 每个浏览器都输出所有字段；有收包就代表完整帧或已显示 |
| 浏览器缓冲/RTT，A/B | getStats中的媒体与候选对统计[S7] | 可用时读取对应缓冲、丢包、候选对RTT/媒体RTT，保持来源与单位独立 | 浏览器RTT代表车端到ZLM；RTT/2等于单向耗时；所有冻结字段必有 |

ROS2有两项必须纠正：

- `std_msgs/Header`包含stamp和frame_id；frame_id用于坐标系标识，不是逐帧递增ID。
  自增调试序号在应用观测记录中另建，不能改写坐标系标识来追踪帧。[S19]
- `sensor_msgs/Image`把stamp定义为采集时间，但具体驱动、ROS时钟和同步质量仍需检查。
  Topic Statistics的消息年龄/周期属于可选能力，要核对rclcpp/rclpy、发行版及配置；
  首版自己在已有回调计数，不依赖内建统计或额外订阅探针。[S20][S21]

两项恢复/时延限制：

- ZLM已有重拉逻辑不代表按用户希望的时间恢复；重试等待本身就可能占据数秒。
  本次固定快照可确认存在等待调度，只能用来指导现场审查，不能替换2025年构建证据。
  特别核对源断开是否连带注销媒体或关闭观看者，避免车端恢复了还需手动刷新。[S23]
- 通过HTTP按秒读取ZLM统计只能证明采样窗口内的进展，不能据此承诺500ms内定位。
  亚秒本地提示可由播放器/车端看门狗建设，ZLM侧若也要求亚秒检测则需确认更新周期
  或接入事件/埋点；不会自动通过缩短轮询间隔获得更高测量精度。

确定可建设的第一条观测链：

```text
ROS2应用收到消息
 -> GStreamer编码输入/输出进展
 -> ZLM输入进展（有可验证字段，否则补最小探针）
 -> 浏览器收包
 -> 浏览器解码/可取得的呈现进展
```

先在这条链上验证源停、编码停、上传停、浏览器消费停及恢复。
动态码率、每帧端到端延迟、逐peer出网和基站级归因仍为独立能力，不能由上述探针自动推出。

## 3. 网络观测实施合同

### 3.1 先把每个数据源绑定真实连接

连接清单包含：

- 逻辑流/车辆/摄像头/观看者、应用会话epoch、进程实例/启动ID。
- 每段实际协议、接口、网络命名空间、方向和脱敏的本地/远端地址端口。
- WebRTC选中候选对、host/srflx/relay类型与所用传输；切换时创建路径epoch。
- RTSP媒体实际TCP或UDP、对应RTP/RTCP连接；TCP控制连接不代表媒体也走TCP。
- SSRC、必要的序号/时间戳映射与ZLM前后映射；中转、RTX、加密封装不能直接混算。
- NAT内外五元组通过会话/探针关联，不能要求两端地址逐字相等。

RTCP、STUN及遥测的反向路径也要观察。媒体到达但反馈回不来，与媒体前向链路断开
是不同故障；RTT本身不区分前向和反向耗时。[S6][S7]

### 3.2 现有RTSP路径按实际承载采集

| 承载/层 | 必须核查的指标 | 不允许的外推 |
| --- | --- | --- |
| TCP媒体 | 每连接RTT/RTO、重传增量、未确认/待发、发送与接收队列、读写进展 | RTP层看不到缺包，不代表TCP没有重传或等待 |
| UDP/RTP | 两端序号范围、乱序/重复、接收缺口、RTCP反馈、完整帧间隔、socket丢弃 | 序号缺口不直接等于空口丢包；必须排除本地丢弃和采集缺口 |
| 主机接口 | 每接口收发、错误/丢弃、qdisc积压、驱动支持的计数 | 网卡总丢包不等于该视频流丢包 |
| 模组/网关 | 注册/连接、可用信号与切换事件、局部连接错误、温度/重置 | 信号弱或小区ID改变不能单独证明卡顿根因 |

Linux现场候选工具为只读的 `ss -tinm`、`ip -s -j link`、
`tc -s qdisc show`、`ethtool -S`；需要按活动连接/接口过滤，核对内核、权限及驱动支持。
正式采集使用结构化接口/应用计数，不能依赖固定格式的shell输出解析。
`ss`的TCP统计与Linux接口统计语义见[S13][S14]，不能将所有计数当作同一分母。

如果需要继续分离“用户态send -> 内核排队 -> 驱动发送”，评估可选socket timestamping；
必须实测支持和开销，不能把软件时间戳当作无线空口真实发包时间。
内核/硬件时间戳有不同采集点与时钟域，缺失时应保留S2/S3之间的未知区间。[S16]

### 3.3 WebRTC上传、下行分别采集

两段分别保存候选对RTT、媒体RTCP RTT、收发速率、反馈新鲜度、丢包/重传、
NACK/PLI、完整帧/解码进度和连接状态，实际支持字段以版本能力表为准。

- 候选对STUN RTT与媒体RTCP RTT分别命名，不混成同一个“延迟”。[S7]
- 标清统计属于上传还是下行、发送者还是接收者。浏览器统计不能替代上传统计。
- 丢包/重传计算使用同会话、同方向、同一窗口；计数归零/重连另起基线。
  统计定义不允许直接做差或相加时只并列展示，不编造端到端丢包率。
- RTCP jitter按对应时钟频率解释；不要直接把原始RTP时间单位显示成毫秒。[S6]
- PLI是刷新图像的请求，不等于丢包数量；频繁PLI支持检查恢复问题，不单独证明网络差。
- 估计可用带宽属于估计，不当作真实链路容量；字段缺失不补0。
- ZLM/GStreamer没有逐会话输出接口时，先列需补的探针，再对照协议协商/实际反馈；
  不用全局流量API冒充已实现逐流观测。

### 3.4 中间网络与路由定位的能力边界

有控制权的VPN、TURN、网关或云入口，分别增加入/出流与队列证据。
无探针的5G空口、运营商核心网和公网，只能圈定为“边界A到B之间异常”；
要细分必须获得运营商或中间节点证据。

ping/mtr/HTTP探测是辅助证据，记录目标、协议、路径和测试时间。
它们可能不走媒体的相同五元组/队列；不能通过相减几个ping RTT计算某一跳单向延迟。
不对媒体注入高负载带宽测试，不假设浏览器公开全部本机WiFi或路由信息。

## 4. 时间、数据字典与采样

### 4.1 分段时间账本

本节是增强能力的目标账本，不是首版硬前提；首版按第2.3节使用各端独立进展和本地时间。
关联同一源帧，尽可能记录：采集、编码入/出、用户态发送、支持时的内核发送、
云端接收、ZLM成帧/转发、播放端接收、解码完成、呈现。
同机阶段用单调时钟；跨机记录时钟偏移/误差、同步状态和时间戳来源。

仅在映射和时钟可信时计算各段时间差；未知帧映射、不同SSRC、重连、时间跳变及丢帧
会中断该次计算。不能用RTT/2代替单向时延，不把重叠阶段或两次RTT直接加成总延迟。
缺某个采集点时展示合并区间，不能把未观测耗时记为0。

### 4.2 最小观测记录

| 字段组 | 必须说明的内容 |
| --- | --- |
| 关联 | stream/camera/viewer、节点启动ID、session/path epoch、segment、方向 |
| 时间 | 本地采样时间、单调时间、接收时间、窗口起止、时钟误差及质量 |
| 指标 | 名称、值、单位、计数/速率/估计类型、分母及所属协议层 |
| 来源 | API/协议/内核/设备、版本、接口/连接/SSRC范围、采样间隔 |
| 数据状态 | unverified/available/stale/unsupported/forbidden/error/not_applicable；缺失原因和最后有效时间 |
| 事件 | incident ID、事件序号、发生/检测时间、证据引用、动作/结果和恢复尝试ID |

应用内部帧号、地址、连接ID进入有界事件/追踪记录，避免全部作为时序数据库标签造成
无界基数。高频采集保留本地有界环形缓冲，按秒汇总上报；故障时冻结前后窗口。
采样/保留预算建议从本地250ms、汇总1秒、前后各60秒事件窗口起试，按车路数和开销校准；
源帧探针记录时间不意味着逐帧全部上传，不保存视频正文或认证报文。

需要抓包时按活动连接、时间和容量限制，在授权环境执行；日志默认脱敏。
遥测丢失、上报迟到、时钟失准本身产生观测故障事件，不能伪造成媒体全线丢包。

## 5. 故障定位规则与值班检查顺序

定位输出固定包含：受影响范围、异常区间、证据、反证/未知、下一步检查、恢复动作。
区分三种证据等级：

- 已定位：匹配同连接/帧、同窗口，且相邻边界或本地探针能直接支持。
- 疑似：相关指标异常，但缺少边界或因果证据；注明待补的探针。
- 未知：数据缺失/不一致/多个候选；不自动选择一个“最可能”当作事实。

| 现象与组合证据 | 可给出的结论 | 下一步检查与动作 |
| --- | --- | --- |
| S0源帧号停止，后续自然无帧 | 采集侧首先异常；具体驱动/ROS2原因待查 | 查源/订阅/本地错误，不重建浏览器掩盖问题 |
| S0持续、S1编码产出停止或耗时增加 | 编码/本地媒体段异常 | 查编码队列、线程、温度/降频；局部恢复 |
| S1持续，S2发送积压或本地丢弃有证据 | 车端发送段异常或受下游反压 | 查qdisc/socket与S3反馈，不能仅据积压认定网卡坏 |
| 车端边界已观测发出，云端未到，S2/S4无本地异常证据 | 疑似S3上传区间 | 核查双向反馈、VPN/中转/模组；无内部探针不指认基站 |
| 云端NIC同流包已到，应用接收/处理晚 | 云端接收/处理区间，细分S4/S5需socket时间证据 | 查内核丢弃、接收队列、ZLM线程负载 |
| ZLM收帧及时，转发驻留增大 | S5内部处理异常有依据 | 查缓存/调度/关键帧等待；排除单个下行反压 |
| ZLM出流正常，一个浏览器接收停止 | 疑似该观看者S6/S7 | 查下行反馈/候选路径/本地网络，不默认重启上传 |
| 浏览器收包推进但完整帧/解码/呈现停止 | S7/S8媒体完整性或播放段 | 查帧完整、关键帧、格式、解码负载/页面状态 |
| RTSP/TCP的RTP丢包低，但TCP重传与停顿同窗升高 | TCP交付等待值得排查，尚不能确定实际丢包位置 | 查两端TCP/队列；不能用RTP低丢包否定网络故障 |
| RTT稳定500-1000ms且媒体连续到达 | 高延迟，可保留会话；画面新鲜度单独判断 | 自适应/告警，避免仅因延迟阈值触发重连 |
| 全部观测一起消失，但媒体部分仍在工作 | 观测链路异常或未知 | 查C1及本地记录，不宣布所有媒体连接断开 |

值班顺序：先确认L0影响与观测新鲜度，再从最后正常/首个异常边界定位；
分别检查正向媒体和反向反馈，最后补查模组/设备事件及恢复动作时间线。
多个区间同时异常可并列报告，禁止用固定优先级掩盖第二个故障。

## 6. 故障界面与记录的验收形态

不另做静态“绿色拓扑演示”；落地界面需能展示实际节点与缺口：

1. 顶层显示车辆/摄像头/观看者、当前画面年龄、连接和媒体两类状态。
2. 链路图区分正常、降级、无媒体、断链、未知；缺探针的网络区间明确可见。
3. 点击异常段，展示同窗收发/队列/RTT/错误及对应会话，不拼接不同重连前后的数据。
4. 事件时间线关联故障、告警、降码率、重连、关键帧与恢复；显示通知是否已送达。
5. 定位卡片给出“区间 + 证据等级 + 下一步检查”，不能只显示“网络不好”。
6. 仅当新鲜可解码/可呈现帧满足约定条件后确认恢复；迟到遥测不改写当前状态。

## 7. 持续500ms以上延迟的专门验收

保留连接与画面满足远控预算是两个验收项。
“持续500ms以上”没有上界、丢包率和最低带宽约束时，不能承诺绝不断连。
需在O1明确范围；RTT、单向延迟、curl耗时、采集到呈现年龄分别命名。

建议测试合同：

- 上传、下行分别注入500/800/1000ms RTT，再测两段同时恶化；测量实际RTT。
- 固定延迟且不额外丢包时，供给足够带宽、媒体/反馈持续推进；各组合建议至少30分钟。
  验收为“无仅由延迟阈值触发的销毁/重连、画面状态如实呈现”，不是画面必然满足时限。
- 再分别叠加受控抖动、带宽不足、随机/突发丢包和反向反馈受阻，记录条件与结果。
- 协议栈或服务端超时导致断开也计作本组合失败，明确是哪一段、哪个版本/层触发，
  不能排除后宣称“应用没有主动断所以通过”。
- 发现短时disconnected，允许在限定观察期恢复；真正失败按状态机重连。
  保活和超时按实测兼容性调整，不关闭协议必要检查或无限放大超时。[S11][S12]
- netem设置与计时需写明方向；端到端RTT不等于每个网卡的单向delay参数。
  在专用测试链路/命名空间操作，不能直接对车辆控制网络注入故障。[S15]

| O9 故障与现场验收 | O9.1逐段故障注入；O9.2持续高RTT；O9.3资源开销/断遥测；O9.4小范围回退 | O6-O8；测试/运维 | 定位、通知、恢复和开销均达约定预算，形成每组合的通过/失败报告 |

建议执行批次：

1. O0/O1先行，冻结一车一路的环境和数据合同。先做字段可获得性核验，
   输出available/unverified/forbidden/unsupported清单，明确代码修改与主机权限前提。
2. O2/O3/O4先围绕M0/M1/M3建设；先接现有RTSP，不等协议迁移。
   M1不可取得时先交付较粗边界，单列最小ZLM探针；M2按诊断价值再补。
3. O5/O6按真实边界建立可定位基线；O7与各端故障检测同步推进。
4. O8验证改进，O9逐段故障与高延迟对照。
5. 满足合同后才按主方案V7小范围切换；保留原链路与回退证据。

首批验收先人工停源、停止上传或暂停播放端消费，检查进展计数、故障提示与恢复。
字段可用后再做需要额外权限的内核探针或网络注入，不让“全部指标齐全”成为首批开工门槛。

### O9 最小注入清单

| 用例 | 预期定位或明确的未知区间 | 必验行为 |
| --- | --- | --- |
| 源停帧、编码停顿 | S0或S1 | 不误报5G故障，局部恢复 |
| 车端本地排队/丢弃 | S2，外部反压可能并存 | 有队列/接口证据，不仅总RTT告警 |
| 上传前向丢包与反向反馈受阻分别注入 | S3相应方向；细分未知需明确 | 能区分反馈缺失与媒体缺失，至少报告边界 |
| 云端接收不及时、ZLM调度阻塞 | S4/S5，按可用探针细分 | 不把主机问题统一归因公网 |
| 仅一个观看者下行受损 | S6/S7对应会话 | 不重启其他会话和车辆上传 |
| 浏览器解码压力、隐藏/恢复页面 | S8或可见性限制 | 保留收包证据，避免重连风暴 |
| ZLM重启、NAT/路径变更 | 会话与路径epoch变更 | 旧回调丢弃，上下游自动恢复 |
| 遥测断开、延迟与时钟跳变 | C1或时间质量异常 | 不伪造媒体故障；本地告警仍有效 |
| 持续500/800/1000ms RTT | 对应上传/下行区间 | 无误断连，画面超龄单独提示，条件和失败不省略 |

每例同时记录：注入点/时间、检测延迟、通知延迟、定位范围、误定位、
恢复起点到首个新鲜帧、恢复稳定时间和误重连次数。
单故障先通过，再做多故障；未知区间由设计决定时标为已知观测缺口，不伪称精确定位通过。
