## 1. 产品承诺

研发人员和团队不仅能让 AI 做事，还能回答：

1. 它正在做什么，下一步是什么？
2. 谁负责，使用哪个模型和工具，为什么这样分配？
3. 是否卡住、失败、超预算，或需要我决定？
4. 产物是什么，有什么证据证明完成？
5. 哪种方案更好，下一次怎样改进？

## 2. 核心能力矩阵

## 3. 首版要能完成的两件事

### A. 调研与方案

用户给出目标和资料，AI 澄清必要问题、建议计划、按需分头研究，最终形成带来源、分歧和待验证项的方案。

不能以“多个 Agent 都说正确”代替证据。来源不可达、信息冲突、结论推断需要分别标记。

### B. 代码修改与测试

用户指定仓库和范围，AI 提出修改计划，授权后在隔离工作区操作，产生 Diff、命令记录、测试结果和审查意见。

不能以“生成了测试”代替“测试执行通过”。未授权不修改主工作区，不自动合并或部署生产。

## 4. 追踪不只是一份聊天记录

最低追踪关系：

```text
项目 -> 任务 -> 运行 -> 计划版本 / 步骤 / 委派
                       -> Agent 调用
                            -> 模型调用及重试
                            -> 工具调用及外部结果
                       -> 审批 / 成果 / 验证证据
```

每次模型调用至少记录：

- 所属任务、运行、步骤、Agent 和调用尝试。
- 请求模型、实际返回模型、Provider 和选择规则版本。
- 开始结束、状态、错误类别、输入输出 Token。
- 总耗时；流式可测时记录首 Token 时间。
- 估算成本、价格来源/时间；不可得时明确未知。
- 经过脱敏的输入摘要和输出引用，而非默认保存原始内容。

追踪元数据与内容采集分开授权。默认不记录密钥、完整环境变量、模型内部思维链或未授权的 Prompt 内容。

## 5. 可分析的内容

| 分析问题 | 需要的证据 | 不应做的推断 |
| --- | --- | --- |
| 为什么慢 | 排队、模型、工具、审批各段耗时 | 总耗时都算成模型延迟 |
| 为什么贵 | 可计量调用、重试、价格快照 | 本地模型成本默认为零 |
| 为什么失败 | 错误、退出码、版本和输入引用 | 将错误摘要当作已定位根因 |
| 为什么返工 | 修改意见、验证结果、重新执行步骤 | 只统计“完成”按钮次数 |
| 哪个模型更好 | 同任务、数据和评测条件下的结果 | 仅按 Token 或角色名称打分 |
| 并行是否有效 | 等待、冲突、关键路径和总用量 | Agent 越多效果越好 |

首版做单次运行分析，不承诺自动优化模型或提供可信的通用质量评分。跨运行比较需控制版本、输入、工具和评测条件。

## 6. 人工控制

权限分为读取、隔离写入、应用变更、外发、部署。审批必须展示实际目标、版本、动作、影响和可用回退方式。

- 暂停请求不等于立刻中断正在执行的外部动作。
- 取消不等于已撤销变更。
- 审批对象变更后需重新授权。
- 发生超时且副作用未知时，进入核查，不直接重试。
- 修改进行中的要求形成新版本，不悄悄改写已经执行的计划。

## 7. 不作为首版目标

- 完整低代码流程编辑器。
- 展示所有模型和 Agent 的大屏。
- 无限递归 Agent、自修改权限或自动训练闭环。
- 复杂模型网关、集群调度、多租户和统一企业门户。
- 同时重建聊天、制品仓库、CI/CD、MLOps 等外部平台。

## 8. 能力验收方法

用固定样例验证两条成功流程和以下失败情况：

模型不可用、工具超时、预算耗尽、审批失效、浏览器断线、部分写入、子任务失败、取消后结果迟到。

用户无需阅读完整日志就能理解状态；需要调查时，能从失败步骤进入关联调用和证据。无法证明的结果显示为“未验证”或“结果未知”，不能显示为通过。
