# 历史草案：设计评审清单

> 已于 2026-11-01 撤回，团队优先和固定流水线不再适用。当前清单见 `../DESIGN_REVIEW.md`。

本文档用于在进入功能开发前，确认产品边界和关键技术决策。

## 1. 必须先确认的产品决策

- [ ] 第一目标用户是研发团队、业务运营团队，还是通用企业团队
- [ ] 首个垂直场景是“需求到 Staging”，还是“业务流程自动化”
- [ ] Agent 是用户可直接创建的对象，还是平台预置角色
- [ ] 用户是否可以自由添加工具和凭证
- [ ] 是否支持跨项目共享 Skill
- [ ] 哪些操作必须人工审批
- [ ] 是否需要多租户和企业 SSO
- [ ] 生产部署是否在首个 POC 范围内

## 2. 推荐的第一版边界

第一版只面向研发团队，聚焦：

```text
需求 → 设计 → 代码 → 测试 → Staging
```

明确排除：

- 生产环境自动变更
- 任意外部消息发送
- 自由创建无限子 Agent
- 自研模型训练平台
- 多云基础设施编排
- 通用企业流程市场

## 3. 设计不变量

以下内容不能被后续页面或实现破坏：

1. 项目、任务、Run、Artifact 是主对象，聊天只是辅助入口。
2. 所有工具调用经过统一权限和审计边界。
3. 每个 Run 必须能够暂停、恢复、重试和取消。
4. 每个 Artifact 必须能追溯到产生它的 Run 和代码版本。
5. 生产级动作必须有明确的审批记录。
6. Agent 只能使用其角色允许的工具和数据。
7. 用户可以在不阅读完整日志的情况下理解当前状态。

## 4. 编排决策

### 推荐

```text
项目编排器
  → 生成显式任务计划
  → 为步骤分配角色 Agent
  → 并行执行独立步骤
  → 汇聚结果
  → 触发质量门禁
  → 进入人工审批
```

### 不推荐

- 无限群聊
- Agent 自主无限递归创建 Agent
- 用单一大模型负责所有角色
- 通过自然语言判断是否可以部署
- 将模型输出直接当作系统状态

## 5. UI 评审问题

- 用户打开首页是否能立即看到“下一步要处理什么”
- 用户是否能从项目进入 Run，而不需要理解 Agent 图
- 当前 Run 是否有清晰的状态、负责人、预算和下一步
- 审批页面是否展示了实际变更和影响范围
- 失败时是否能定位到具体 Step、Agent、Tool 或环境
- 日志是否默认折叠，避免信息噪声
- 移动端是否只保留审批、告警和结果
- 是否所有主按钮都能在键盘上操作

## 6. 设计验收标准

设计阶段完成的标准：

1. 有完整的信息架构和页面层级。
2. 有“需求到 Staging”的端到端用户旅程。
3. 有 Project、Task、Run、Step、Agent、Artifact、Approval 的对象关系。
4. 有 Run 状态机和事件协议。
5. 有 Agent 权限、工具和审批矩阵。
6. 有首个 POC 的成功与失败样例。
7. 有视觉 Token、布局规则和响应式约束。
8. 有明确的第一版非目标。

只有以上内容完成评审后，才进入前端工程和后端 API 实现。
