## 2. 核心判断

**不是再选一个包办所有能力的平台，而是先交付一个能连续工作的产品。**

建议保留 mybot 的项目、权限、发送确认、Run 预算与审计。优先受控复用 OpenMausBot 的 Bot/会话/工作控制；其他项目按功能模块研究，不并行运行多个平台控制同一工作。

| --- | --- | --- | --- |
| OpenMausBot | 长期 Bot、Task/Thread、会话、MCP 工作控制、事件 | 已有 35/38 项受限 mock 实测，原生网络、审批、强制权限/预算未验收；有内部/后台模型请求 | 优先做适配候选，读路径先落业务；不重写整套 Bot 系统 |

## 3. 三种复用方式

1. **能力服务适配：** 例如受控 MCP/HTTP 连接 OpenMausBot；原服务拥有 Bot/Thread/执行事实，mybot 保存引用、授权命令与审计。
2. **局部代码/库复用：** 先检查许可证、宿主依赖和安全边界，保留来源/NOTICE 与契约测试；不能复制 OpenClaw 飞书目录就称为独立连接器。
3. **机制借鉴：** 例如 Cindy 的控制语义、OpenMuse 的结果未知处理、HarnessWorks 的失败回归；用现有工具实现，不复制 UI 或增加无用服务。

有可用库时不用手写核心引擎；不能独立抽取时明确选官方 SDK 或服务适配，不为“复用率”承担整个上游宿主。

## 4. 架构与事实归属

```text
原创 Web：项目 / Agent / 持续会话 / 待处理 / 成果
                         |
mybot API：身份、项目授权、发送预览、预算、命令回执与审计
                         |
               每个 Run 一个执行后端
          +--------------+----------------+
          |                               |
  现有受限研究流程                 OpenMausBotAdapter 候选
  （现有 Provider）               Bot / Thread / 原生引擎
                                          |
                                  选定的一种 Harness

连接器（后续） -> 受限 Channel / Resource / Action
设备（后续）   -> Rust Node / 明确的执行归属
工程治理       -> 现有 CONTINUE / ADR / tests + 精简失败记录
```

不是 `mybot -> OpenClaw -> OpenMausBot -> DSH -> Pi`。

| 对象 | 建议权威方 | mybot 保存什么 |
| --- | --- | --- |
| 项目、用户/设备授权、资料范围、预算、人工决定 | mybot | 原记录 |
| 外部 Bot/Profile、Thread、原始消息、原始执行状态 | 被采用的上游服务 | `backend_id + upstream_id`、版本/游标、只读投影，不竞争改写 transcript |
| Run/发送确认与命令 | mybot | 精确快照/hash、上游回执、命令状态 |
| 上游模型/工具调用 | 上游原生事件，mybot 规范化审计 | 来源 ID、原状态、缺失字段与计量可信度；未知不是 0 |
| 草稿/排队要求 | mybot，直到显式提交 | 服务端草稿/版本；确认后关联 message ID，不能两边重复发 |
| 连接凭证与授权 | 每个连接仅一个受控宿主 | 引用与 scope，不在浏览器或会话正文复制 token |

映射是设计，不是数据库已新增这些表。外部 backend 不是 Provider，不能把外部消息送进现有 planner/research/synthesis 再重复执行。

读取接口无发送动作，也不保证上游启动无背景请求。未准备专用环境、凭证与禁止隐式调用策略时，页面保持未配置，不自动发现本机账号/服务。

## 5. 逐步实现

每步可审阅后进入下一步，不等待所有项目“研究完成”。工期按接入实测估算，不先给无依据天数。

### 第一步：本地 Harness/模型发现，再读通一个后端

**目标：** 在 mybot 找到已授权 Bot、会话和工作记录，不再看 Runtime Lab。

- 最小本地发现：显式环境模型 + CLI binary 状态；不读取 credential store、不自动发连接检查。
- 最小后端接口：连接状态、Bot/会话列表、分页消息、归一化状态；只做实际需要的方法。
- 端点、版本、凭证引用显式配置，凭证只在服务端；默认不自动连接/启动/扫描。
- `workbench/` 新增窄适配层，现有 API/Schema/Store 增量保存 binding；`web/app.js` 增加项目下 Agent/会话入口，沿用成果检查结构。
- 用 MockTransport/隔离夹具验证 API→适配器→UI；fixture 仅测试入口，不写正式数据库冒充用户历史。
- 无发送、停止、修改 Bot 或审批操作；未配置/空数据展示真实状态，不静默降为 mock。

**验收：** 刷新定位同会话；分页不重复；空/断线/403/撤销/schema 变化可区分；backend 绑定不串数据；发现本地 CLI 不触发 Provider；默认模型必须由用户选择或显式环境配置。

**停止条件：** 不能限制上游读取范围或无隐式请求保障，则停在隔离验证，不接当前账号。

### 第二步：受控发送，再持续追问

**目标：** 原创工作区发一次研究要求，得到关联 Run/消息/成果；追问仍在同一会话。

- 先补原生 MCP client 与专用 HTTP 传输验证，不搬研究 bridge 上线；只允许专用 mock 网络，不解除 deny-all 访问任意网络。
- 启动前确认文件/历史片段、模型、位置、权限与全部调用预算；沿用精确快照，检查 profile/模型版本。
- 持久命令 ID 与 `send_id`：记录意图→发送→关联回执；超时标记 `outcome_unknown`，按原 ID 对账，不改 ID 重发。
- 宿主强制工具/目录/网络/调用上限；关闭或审查自动检查、记忆整理、补偿与辅助调用。Ask 模板不等于能力上限。
- 无完整计量时显示未知；不假设一条消息只有一次模型请求。
- 补充要求先存下一轮草稿，不改在途快照；失败后不自动继续队列或切模型。

**验收：** 重复点击/重连不双发；内部请求也计预算；失败/中断/计量未知真实显示；`settled` 不映射为成功。

**停止条件：** 权限/预算在执行边界无法强制，只开放 mock 发送与授权读取，不用前端按钮代替后端策略。

### 第三步：电脑、手机、Pad 往返接续

**目标：** 电脑开始、手机查看/补充、回电脑见到同一会话与成果。

- 可撤销设备会话、命令预期版本、游标补齐；先增量 HTTP/SSE，不先建 Relay。
- 借鉴 Cindy 的身份/能力/在线三态、nanoMuse 的来源/游标；mybot 持久事件不被上游临时推送替代。
- 先浏览器，桌面/Pad 并排，手机单主面板；客户端平台和执行服务器平台分别标记。
- 远程需明确 HTTPS/私网入口，不自动放开监听。控制浏览器关闭不停止中心，中心离线不能伪装持续执行。
- 用户新增的 Headscale 是可选自托管网络控制面，专项见 [REA_HEADSCALE.md](REA_HEADSCALE.md)；不代替应用会话/项目 ACL，也不成为第一步 UI 的前置依赖。已有 VPN 可直接评估使用，不重复建设。

**验收：** 独立设备授权、断线补齐、锁屏返回、双端冲突/去重、撤销；尺寸截图和真机分开。

多用户共享在有 Membership/项目 ACL 前不启用，共享令牌不是团队身份。

### 第四步：一个 IM + 一个资料源

**默认建议飞书 + 语雀只读**；用户日常以钉钉为主则替换首个 IM，不并行铺所有渠道。

- IM 首期只查状态、脱敏通知、创建草稿和回 Web 链接；外部“好的”不是花钱/写入授权。
- 资料仅指定库/片段，保留来源版本/ACL，入模型仍确认，不索引全账户。
- OpenClaw/QwenPaw 参考身份/话题/生命周期；先比较官方 SDK 窄连接器与受控现成服务，不启动第二个默认 Agent 回复循环。
- 签名/身份→Inbox 去重→租户/账号/话题映射→项目授权→草稿→明确执行→Outbox→回执。
- 微信、钉钉、邮箱随后逐一验收；“支持微信”不是全历史/联系人/任意 App 控制。

**验收：** 先协议夹具再单独授权测试账号；重复事件、越权、撤销、提示注入、未知回执、限流、敏感外发有测试。

### 第五步：研发执行与可核查成果

**目标：** 在受控环境完成一项研发变更，交付可审查证据。

- 独立新增代码执行授权/沙箱阶段；固定测试仓库、隔离 workspace/worktree、有限命令，不部署。
- 一 Run 一执行器；可保留 OpenMausBot 驱动或直接 Pi/Codex 等路线，不用两套循环重复分工。
- 借鉴 OpenMuse 的 Task/Artifact/Receipt 与 lease/CAS；对照真实 diff、退出码和测试，不把模型 finish 当验证通过。
- 人工决定绑定成果版本；文件/权限/目标变化需重批，未知副作用不能自动重做。

**验收：** 实际 diff/命令回执、失败/取消/进程树退出、重启核查。当前只读授权不自动覆盖此阶段。

### 第六步：Rust Node、原生壳与迁移

- Rust 先 Linux Node：配对、心跳、能力范围、受控进程/传输，再做 Windows 原生路径/ACL/进程树；TS 渐进用于界面/连接器。
- 必须托盘/通知/系统能力时再做 Tauri/原生壳；HuLa 仅机制参考，不复制 UI。
- 先控制另一设备，再任务路由，最后支持检查点的归属迁移；不承诺搬活进程。
- iPhone/iPad 默认控制端；任意 App 控制、后台常驻、屏幕操作分别验收。
- 按长记录、慢网、CPU/内存和增量同步测性能；无数据前不重写中心、不宣称 Rust 必定更快。

## 6. 精简工程门槛

参考 HarnessWorks 思想，沿用已有记录与测试，不安装治理框架：

1. 未显式启动/测试，不产生外部模型请求。
2. fixture 不进入正式运行，不在错误时静默 fallback。
3. `settled`、完成、测试通过、人工接受分开。
4. 一 Run 一执行权威；重复命令不双发。
5. 权限/范围/费用未知/副作用未知不得靠自然语言或默认配置抹掉。

真实缺陷各补一个针对性 fixture/回归；按既有 ADR/台账维护来源。指标看旅程完成、越界、重复请求、首次验收和人工返工，不看文档/页面/测试数量代替效果。
