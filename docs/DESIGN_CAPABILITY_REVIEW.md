# 多版本设计与组合能力评审

评审日期：2026-11-07，以本轮环境日期为准。状态：针对用户“没有达到效果”的分析与调整建议，尚未获最终产品/视觉确认。

本文不替代 [ADR-0004](decisions/ADR-0004-implementation-slice.md)，不扩大当前只读执行权限，不宣称接通上游。历史稿和测试证据全部保留。

## 1. 直接结论

**可以朝 Cindy + OpenMausBot / nanoMuse 的组合能力演进，但现有多个设计版本和真实应用都还没有做到。问题不是缺少几个页面，而是日常工作对象和闭环缺位。**

- V1 偏任务管理后台，缺少长期协作对象。
- V2 的工作记录与成果并列值得保留，但它主要描述单次研发执行，不是持续使用的多端 Agent 产品。
- Runtime Lab 是协议研究/开发诊断页。把它作为“继续产品并可预览”的主要交付，偏离了用户想体验的工作流程。
- 真实 `web/` 有持久运行与审计基础，不能因静态稿出现编码、测试、审批，就宣称具备这些执行能力。
- 下一轮不再新增并列的独立演示站点；先在同一个工作台里完成“找回助手与会话、接着交办、检查成果、换端继续控制”的最小闭环。

建议目标：

**长期可配置的 Agent + 项目内持续会话 + 多端控制同一工作 + 可授权的应用能力 + 可核查的研发成果。**

这不是将四个平台及其账号、数据库、Agent 主循环拼在一起，也不是退回只有聊天气泡的通用 Chatbot。

用户随后追问“OpenMausBot 能力已经有了吗”：**OpenMausBot 上游已有长期 Bot、持续会话、手机共享工作区、执行与连接应用机制；缺的是 mybot 的接入与验收，不是这些能力从未存在。** 下一轮应优先验证能力复用，不默认重写 Bot/会话系统。第 7 节列的是逻辑需要，不是要求全部自研表与执行器。受限 Bot API 也不是唯一入口；上游还公开了更丰富但不开放审批授权的 MCP 团队控制接口，见调研第 11 节。

## 3. 各版本如何取舍

| 版本/迭代 | 有价值的部分 | 未达到效果的原因 | 建议处置 |
| --- | --- | --- | --- |
| V1 | 执行/验证/人工决定分离；失败与未知结果；流程覆盖 | 列表和隔线主导，信息分散，像管理运行记录；缺少可持续交办的对象 | 保留流程与历史，不恢复为视觉基线 |
| V2 任务/调用 | 工作记录与成果检查并列；手机面板切换；调用溯源 | 一个固定编码样例撑起全部体验；没有真正可用的持续输入、会话列表、长期 Agent | 复用工作区结构；正文和成果随真实任务变化 |
| V2 协调/Control Panel | 委派依据、预算与下一次配置差异 | 全局 Super-agent 与任务协调重叠；控制/调度/调用入口分散，用户要先理解内部架构 | 协调放回工作流；当前工作设置就地展开，全局默认配置另存 |
| V2 计划修订 | 失败证据关联新计划，旧授权不自动继承 | 仍是本地草稿，不能把改要求真正送入下一轮工作 | 保留版本关系；后续连接真实新任务/Run，而非改写历史 |
| Runtime Lab | 统一事件、取消和未知状态的夹具检查 | 三个引擎并列和原始协议抢占主体验，不能体现实际协作、接续或应用能力 | 仅作开发诊断候选，保留独立文件，不推荐为产品首页 |
| 真实 Web | 持久数据、发送快照、有限分工、成果与审查 | 使用路径仍是配置模型、创建任务、检查一次 Run；不能长期对话或切换 Agent | 下一轮业务增量所在；不另建新后端/事实源 |

`prototype/` 是未采用的早期草图，不加入候选基线。V2 是当前最值得复用的结构，不代表配色、排版或交互已获认可。

### 具体问题与源码定位

1. **缺少长期 Agent。** [store.py](../workbench/store.py) 的 `agents` 表要求 `run_id`，表示运行中的角色实例，不是可保存模型、能力范围、项目和版本的 `AgentProfile`。
2. **工作记录不是持续会话。** [V2 review.js](../design/review-v2/review.js) 的 `task()` 输入框为 `readonly`，发送禁用。真实 [app.js](../web/app.js) 的 `runView()` 也没有会话消息输入与消息持久化；现有补充意见只记录人工决定。
3. **固定编排不等于通用 Agent。** [engine.py](../workbench/engine.py) 的 `execute()` 固定规划、1–2 个只读子任务、汇总，不能借调用数或角色头像证明任意工具协作。
4. **视觉中的成果能力超前于实现。** V2 将代码 Diff 与测试设为主要成果；当前真实成果是文本调研。文档、邮件和资料研究不应被强行装入代码面板，更不能展示虚构测试成功。
5. **配置与工作混在一起。** V2 的全局协调导航实际指向固定任务；真实导航只有工作台、模型/控制、项目。需要的是稳定的项目/会话入口，不是继续增加同义技术页签。
6. **Runtime Lab 的对比不是完成工作。** [fixture-runtime.js](../design/runtime-lab/fixture-runtime.js) 的 `fixtures()` 拼入用户任务后返回预设正文，`createRun()` 是内存夹具；刷新或动画结束都不产生真实会话/任务能力。
7. **移动布局不是多端接续证据。** 已有截图证明部分尺寸可排版，没有证明两个控制端看同一最新状态、重复操作不产生两次调用，或设备撤销后失去访问。

### 视觉层也需要改

- V1 的空白、细隔线和大量弱层级标签使“下一步做什么”不突出。
- V2 比 V1 更接近研发空间，但标题、状态轴、多个页签及协调入口占据注意力；正文、可交办入口和当前成果应成为第一层。
- 深色不是高级感的验收标准。先评审正文可读性、密度、对比、主次和跨任务可用性，再决定颜色与明暗主题。
- Agent 名称与职责应稳定可辨，不依赖单个字母头像、模型名或颜色辨认角色；无需复制上游人物、动效或聊天 UI。
- 工程日志、原始 JSON、Token 统计作为按需检查内容，不挤进每次对话的首屏。

## 4. “组合能力”究竟借鉴什么

本节是固定快照的源观察与本地设计建议，不是性能排名或集成结果。

| 参考 | 值得借鉴的机制 | 不直接继承的前提 |
| --- | --- | --- |
| Cindy | 控制端/执行端分离，同一工作跨屏查看、追问、授权；设备协议、重连和能力协商 | 手机主要是控制端；文件仍在原电脑，电脑需在线。公开客户端不包含完整服务端，不能据此获得独立私有云 |
| OpenMausBot | 长期 Bot、独立对话与工作范围；手机 Web 使用同一工作区和会话；配对/撤销 | 不是“没有跨端上下文”。其手机 Web 文档也明确不带离线聊天、推送或原生手机控制；本地 P0 不等于底座验收 |
| nanoMuse | 会话同步与设备委派分开；来源/owner/cursor；任务、审批和停止跨端返回 | 文本同步不是文件同步或活进程迁移；各端能力、在线状态和历史同步范围不同；GPL 代码复用另审 |
| QwenPaw | Channel 入站归一化、身份/ACL、插件和连接器生命周期 | 接上聊天入口不等于开放写文档、发信或 GUI 权限；尚无 mybot 真实连接器证据 |
| Pi / 其他 Harness | 作为受控可替换执行器，输出规范事件和真实能力 | 不让多个主循环共同控制同一 Run；选引擎不是产品首页 |
| HuLa | 后续客户端平台、消息补齐和原生壳边界参考 | 不复制 UI，不作为 Agent 内核，不因此重写现有 Web |

Cindy 的设备控制、OpenMausBot 的多 Bot、nanoMuse 的统一对话不是同一层能力。建议在 mybot 合成为：

- 一个项目有多条持续会话，每条有一个主要 Agent；按需委派其他 Agent，结果仍能回到原会话定位。
- 长期 Agent 是职责、模型偏好与能力模板，不是另一个隔离产品或数据库；项目授权始终独立校验。
- 同一会话可关联多项任务和多次 Run，明确哪条消息触发哪次执行。
- 所有控制端看同一持久事实；先只控制现有中心执行，不在手机另开一个 Agent 主循环。
- 不强制所有项目共享一条“大主聊”，也不让每个 Bot 的文件夹成为独立且不可治理的信息孤岛。
- 长期会话不等于把全部聊天自动发给模型。每次发送的资料、历史片段和成果引用仍需形成可确认的上下文快照。

仓库身份、完整 commit、路径、许可与 unknown 见 [OPEN_SOURCE_RESEARCH.md](OPEN_SOURCE_RESEARCH.md) 第 9、10、11 节；模块编号沿用 [OPEN_SOURCE_ADOPTION_MAP.md](OPEN_SOURCE_ADOPTION_MAP.md) 的 M01–M19。

## 5. 能力差距矩阵

“部分”表示已有相关基础，不表示目标已验收。

| 用户能力 | 当前真实应用 | 现有设计表达 | 下一项必要增量 |
| --- | --- | --- | --- |
| 项目/任务/成果持续保存 | 有 | V1/V2 有 | 保留，不重建事实源 |
| 长期可配置的多个 Agent | 无；只有 Run 内实例 | V2 仅本轮角色 | `AgentProfile`、版本与项目能力范围 |
| 多会话、持续追问与修订 | 无 | V2 有禁用输入框 | `Conversation/Message`、运行关联、历史与检索 |
| 同一工作在手机/Pad/电脑继续控制 | 部分：服务端 Run 可查询、响应式界面 | 缺少完整往返旅程 | 可撤销访问、同步游标、命令去重/冲突、网络验收 |
| 并行协作而非模型横向对比 | 部分：最多两个研究子任务 | V2 有委派，Lab 不是协作 | 长期角色映射与任务委派/成果回链 |
| 运行中补充要求 | 无 | 静态输入，不可执行 | 先持久排队给下一轮；不改在途快照 |
| 换电脑执行或远程操作本地文件 | 无 | 无完整设计 | Node、路径/权限、归属、在线状态与故障协议 |
| 飞书/钉钉/微信聊天入口 | 无 | 没有可用连接流程 | Channel、账号绑定、Inbox/Outbox、权限与回执 |
| 语雀/邮箱等资料读取 | 无连接器；只有显式本地文本 | 仅资料引用概念 | Resource、范围授权、来源版本与发送确认 |
| 发信/写文档/编码/跑测试 | 无 | 部分静态样例 | 分别建立动作审批、回执、受控执行与验收 |
| 原生壳/推送/离线 | 无 | 响应式不能证明 | 按实际需求专项，不作为首期门槛 |
| 团队成员与项目 ACL | 无；共享令牌不是用户体系 | 静态所有者/权限提示 | 身份、成员关系、逐请求权限，另作团队阶段 |

## 6. 同一个工作台如何组织

这是下一轮信息架构提案，不是新增了这些页面。

### 第一屏

有历史时恢复最近会话；无历史时直接提供创建项目/选择 Agent/开始工作的空状态。待处理入口显示等待输入、失败和结果待审，不做泛化统计仪表盘。

桌面结构：

```text
项目 / 会话列表 | 持续会话与工作流               | 按需成果检查
               | 主 Agent、当前任务、执行位置    | 方案 / 来源 / 后续 Diff
               | 计划、进展、问题、成果引用      | 对应版本与验证
               | 输入 + 本次资料/模型/权限      |
```

侧栏优先列项目、最近/置顶会话和待处理事项。Agent 管理、连接与设备是清晰可达的次级入口；模型、Harness、原始协议不占主导航第一层。

### 五个必要空间

| 空间 | 用户真正需要做的事 | 避免 |
| --- | --- | --- |
| 工作/会话 | 持续交办、选择 Agent、关联任务、检查成果、补充要求 | 只能查看流水账，或每次从模型配置重新开始 |
| 我的 Agent | 保存/编辑职责、默认模型、项目与能力模板、查看近期工作 | 把创建 Agent 等同授权全部目录或应用 |
| 待处理 | 回答问题、审查成果、处理失败；未来展示真正的动作审批 | 一个“批准”同时代表接受文本、花钱、写文件和发邮件 |
| 连接与设备 | 区分应用授权与执行节点；看范围、在线/测试时间、撤销 | 未实现设备的假在线点，或把保存配置标作已连通 |
| 检查与诊断 | 从消息/成果定位任务、Run、调用和审计；开发者可看 Lab | 用户工作时被迫读原始事件和理解协议 |

手机不是压缩桌面三栏：会话为主，成果独立面板，待处理能直达原会话；平板按可用空间展开。运行位置与最后确认时间可见，但未接 Node 时只能如实显示中心执行，不能制造“Linux Node 在线”。

Agent、模型、连接、执行位置四者分开：换模型不自动增权；选择 Agent 不自动连接第三方；切控制设备不改变执行位置。

## 7. 最小工程增量

保留 `workbench/` 的持久运行、事件、发送快照与预算，保留原创 `web/`；不全量 Rust 重写，也不同时重做前后端框架。

实现路径先做复用判断：用隔离 mock 检查 OpenMausBot 的 MCP/HTTP+SSE 能否安全覆盖 Bot、会话和工作控制。若采用，由适配器提供稳定上游 ID 与状态映射，明确每类数据的权威方；mybot 不再另建一套竞争写入的会话真相。若权限、审计或接口不足，再按缺口局部自建。当前未决定采用，也未证明 MCP 本身能构成只读权限上限。

| 层 | 最小新增 | 约束 |
| --- | --- | --- |
| 长期工作对象 | `AgentProfile(version)`、`Conversation(project, primary_agent)`、`Message`、消息与 Task/Run 关联 | 模板修改只影响新运行，已有 Run 保留模型/权限/输入快照 |
| 追问与执行 | 保存消息；显式准备新任务/新 Run；展示继承的成果和本次发送范围 | 运行中补充先排队给下一轮；不静默注入在途调用，不重写旧 Task/Run |
| 跨端访问 | 可撤销单用户设备会话；服务端身份绑定与访问校验 | 当前共享令牌不足以完成单设备撤销；配对凭证、会话期限和登出单独设计 |
| 命令/同步 | 幂等命令 ID、预期状态版本、回执、持久事件游标与补齐 | CAS 处理同时操作；取消不是撤销，断网不是成功，结果不明不重放 |
| 资料/应用 | 后续 `Connection`、`CapabilityGrant`、渠道绑定和动作回执 | 配置保存、连接测试、业务往返分别记录；通知也有外发范围 |
| 设备执行 | 后续 Rust Node 与能力协议 | 先 Linux，再 Windows 原生验证；不让控制权与执行归属混同 |

首步无需改造为任意自主 Agent loop；持续会话可以先驱动现有受限研究流程。真正工具循环与执行器接入另过权限、取消、恢复和用量合同。

性能先处理增量更新、分页、长记录与背压；Rust 优先用于未来常驻 Node、传输和受控进程管理，TS 渐进用于界面/连接器。当前没有性能基准，不以语言推断快慢。

## 8. 迭代顺序与可见交付

对 [多端方案](MULTI_DEVICE_AGENT_PLAN.md) 的补充：身份/权限仍是远程门槛，但执行器 P1 不应阻塞会话产品增量。以下是体验交付顺序，不是已批准的工期或能力扩权。

| 迭代 | 用户能看到的结果 | 借鉴与证据 | 不混入 |
| --- | --- | --- | --- |
| A：持续工作 | 优先验证复用既有 Bot/会话；保存一个 Agent；追问形成新一轮工作；旧成果可定位 | OpenMausBot M02/M11 + 自有 M01；隔离适配验证后再接业务 API、测试持久与恢复 | 新 Lab、默认样例任务、任意工具权限、未经比较就重写 |
| B：同一人多端 | 两个独立已授权浏览器看同一工作；手机补充/审查，桌面同步；撤销与重连 | Cindy M04/M05、nanoMuse M06/M07；并发/断线/去重及真机证据 | 执行迁移、离线 Agent、假手机兼容认证 |
| C：一个应用闭环 | 飞书或钉钉之一产生草稿/查询状态；语雀只读资料按需入快照 | nanoMuse/QwenPaw M09/M10/M12/M13；假适配器到明确授权真实账号 | 一次装全渠道、自动模型调用、直接发信/写文档 |
| D：设备执行 | 明确选择在线 Linux Rust Node，后续 Windows；统一运行与权限合同 | Cindy/nanoMuse 设备机制；候选 Harness 按合同验收 | 搬活进程、复制凭证、自动提权 |
| E：扩展动作 | 邮箱只读/草稿，再独立审批发信/文档写回；编码/GUI 另过沙箱验收 | 已有逐项目 REA 计划与动作回执 | 将“支持 App”当作全 App/全权限可控制 |

OpenMausBot P0/P1 继续用于决定是否采用其执行能力，不是 A/B 开始的前置条件。默认 Full、模板可跳过/覆盖、Ask grants 等已知问题不因 UI 改善而消失。

REA 持续用于合适的发布包与隔离运行取证，完整源码分析仍用常规工具。每次只验证一个待采用机制，不用新增 REA 报告数量替代产品交付。clone、固定 commit、隔离、复现与清理方法沿用 [UPSTREAM_CLONE_AND_IMPLEMENTATION.md](UPSTREAM_CLONE_AND_IMPLEMENTATION.md) 和 [REA 索引](REA_PROJECT_BREAKDOWNS.md)。

## 9. 第一条必须走通的验收旅程

**“Linux 开始调研 → 手机接着查看/补充 → 回电脑继续 → 找到同一会话与可核查成果。”**

1. 桌面保存“研发研究员”的职责、默认模型与只读范围；刷新后仍在，换项目不会继承额外权限。
2. 在项目会话中交办，查看真实发送快照和预算后才开始；实际调用仅在用户显式触发时发生。
3. 同一会话内看到当前任务、分工与成果引用；无测试执行时明确无测试，不能使用 V2 编码样例装饰。
4. 另一已授权手机控制端打开同一会话与同一 Run；桌面浏览器关闭不应取消中心工作。
5. 手机上补充要求，持久保存为下一轮草稿；原 Run 输入不变。当前轮结束后明确确认新资料/成本再启动下一轮。
6. 两端同时提交相同命令不产生双调用；并发不同要求提示冲突或保留排队关系，不静默覆盖。
7. 手机暂断网后补齐记录，不能靠重发任务恢复；离线时显示最后确认时间，不能展示“已取消”假成功。
8. 回桌面能定位手机消息、新 Run、旧成果与新成果；不要求用户打开 Runtime Lab 理解发生了什么。
9. 撤销手机访问后，该端刷新、重连和发命令均被拒绝；更换设备不会同步中心凭证。

先用明确标注的测试 Provider、独立临时库验证；真实模型、TLS 远程入口和手机真机逐项授权验收。两个本机浏览器只能证明部分协议行为，不等同网络与真机通过。

如果上述旅程仍走不通，就不能将交付称为 Cindy 式跨端接续或成熟多端 Agent 工作台。
