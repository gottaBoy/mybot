# 如何定义现代研发 AI 工作台

更新日期：2026-11-01。

状态：面向研发团队的产品定义提案。目标用户已明确；能力优先级、交互和视觉细节尚待评审。

## 1. 一句话定义

现代研发 AI 工作台，是围绕研发项目，把人、多个模型、Agent、工具和执行环境组织在一起，并以可检查的成果、真实执行证据和可追责的决策闭环交付工作的统一操作空间。

“现代”不是增加聊天模型或画出更多节点，而是：

- 理解项目目标与持续上下文。
- 能执行，而不只回答。
- 能分工，而不靠无限群聊。
- 能追踪与解释执行状态，而不只显示过程动画。
- 能由人中断、审查和接管。
- 能比较结果和复用经过验证的经验。

## 2. 面向谁

目标用户：研发工程师、设计与测试人员、技术负责人和发布运维人员。

首个试点：一名研发人员，在一个限定仓库或研发调研项目中完成工作。

目标产品与试点规模分开：

| 维度 | 当前方向 |
| --- | --- |
| 产品定位 | 面向研发团队的工作台 |
| 首次验证 | 单用户、一个项目、少量模型和受控工具 |
| 团队共享 | 基本身份、项目访问与审批责任先于共享上线 |
| 企业治理 | SSO、复杂组织、跨部门配额等后置 |

前面的偏移不在“团队”两个字，而在过早把体验等同于固定交付流水线和完整企业基础设施。

## 3. 七个必要能力域

### A. 项目与研发上下文

仓库、Issue、需求、架构、设计、API 契约、测试、历史决策和环境作为有版本、权限和来源的引用。

用户不需要每次把整个项目重新描述一遍，也不能因为“项目已关联”就默认把所有文件发送到任意模型。

### B. 工作规划与协作

支持澄清目标、拆解任务、定义交付物、设置验收条件和责任人。任务可以只做方案、只改代码、只运行测试，不必全部到部署。

人与 Agent 的修改、评论、审查、接管都关联同一任务和成果，而不是多个互不相通的聊天。

### C. 多 Agent 与多模型执行

Super-agent 提出计划和委派建议，Subagent 承担有限专业工作，调度器执行依赖、权限、资源和预算检查。

模型选择按能力与约束进行，保留路由理由和实际调用模型。角色、模型和工具是不同对象。

### D. 开发环境与工具

文件、终端、Git、测试、浏览器、构建和部署接口有明确作用范围。代码变更隔离，工具结果有命令、版本、退出码或外部证据。

GPU 和推理运行时是可连接资源，不要求所有用户先搭建 ML 平台。

### E. 可追踪的执行

从项目任务定位到计划步骤、Agent、模型调用、工具调用、审批和成果。

任务图、委派树、时间线和调用表是同一执行数据的不同视角。操作审计与性能追踪分开，不能只靠一份聊天历史替代。

### F. 成果与质量

方案、设计、代码 Diff、PR、测试报告和发布制品可定位、版本化和审查。AI 自述完成、命令执行成功、测试通过、人工验收分开表达。

质量要靠实际评测与证据，不靠“多个 Agent 一致同意”。

### G. 人工控制与分析改进

支持审批、取消、恢复、失败接管；展示预算、等待、重试与瓶颈。比较模型或计划时保留输入和验证条件。

重复成功流程可以形成候选模板或 Skill，审核和评测后发布，不允许自动提升权限或静默修改核心行为。

## 4. 与其他产品的边界

| 产品 | 主要价值 | 工作台如何处理 |
| --- | --- | --- |
| AI 聊天 | 讨论与内容生成 | 作为任务入口，不是全部产品 |
| IDE/Coding Agent | 编辑、终端、代码上下文 | 可接入的研发执行能力 |
| 项目管理 | 目标、需求、任务与责任 | 可连接或保留轻量项目域，不重建完整 Jira |
| CI/CD | 确定性的构建和发布 | 调用、观察、审批，不用 Agent 替代流水线 |
| Agent 平台 | 角色、工具和运行时 | 底层候选，不决定研发体验 |
| LLM 追踪系统 | 调用、用量和评测 | 补充遥测，不作为任务事实唯一来源 |
| MLOps/GPU 平台 | 训练、模型部署与实验 | 专项项目能力，不是所有项目的主界面 |
| 制品仓库 | 镜像、包、扫描与晋级 | 外部服务，不让所有工作成果都经过制品晋级 |

## 5. 一个贯通场景

需求：为已有服务增加可配置重试，并验证不会重复扣款。

1. 人确认问题与验收条件，关联 Issue、仓库和相关接口。
2. Super-agent 建议研究现有实现、修改方案和验证步骤。
3. 研究与测试设计可并行；代码工作区只允许一个明确写入者。
4. 开发在隔离工作区修改，评审读取实际 Diff 与测试证据。
5. 工作台展示失败、重试、模型与工具调用及预算。
6. 人决定是否应用变更或提交 PR。
7. 后续构建和测试环境发布作为独立任务，关联同一成果与版本。

此场景同时验证研发价值、分工、追踪和控制，不需要立即具备生产运维自治。

## 6. 三种工作视角

### 做事视角

目标、计划、当前状态、对话和成果。工程师在这里推进任务。

### 控制视角

依赖、委派、权限、预算、审批和恢复。负责人在这里处理干预与风险。

### 分析视角

调用链、等待与执行耗时、Token、重试、失败、变更和验证结果。调查者在这里定位问题和比较方案。

三种视角共用对象和选择状态，不是三套互不相关的产品。

## 7. 初步方案

自己定义研发项目、任务、成果、审批与追踪契约，建设原创工作台。

优先评估 OpenHands SDK/Agent Server 作为代码执行后端；从 OpenBot 研究能力边界、委派与审计设计；从 OpenMuse 研究任务内可见执行、预览和人工接管的体验原则。

这是待技术 POC 验证的取舍，不是直接拼装三个完整项目。不开三个运行时来重复管理任务、凭证和记忆。

开源证据与缺口见 [OPEN_SOURCE_RESEARCH.md](OPEN_SOURCE_RESEARCH.md)。当前仍在设计和研究阶段，没有确定全部技术栈。
